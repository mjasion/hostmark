# Decisions

This file resolves ambiguities in [`spec.md`](spec.md) and records deliberate deviations from it. **It
takes precedence over the spec.** When implementation forces a new decision, add an entry here in the same
change.

## Repository and process

**D1. Name and workflow.** The project is `hostmark`, packages use the `@hostmark/*` scope, and the licence
is `GPL-3.0-only`. Work is committed directly to `main`; the owner chose this over the spec's "each adapter
in a separate PR". Smoke test results go in the commit message or adapter README instead of a PR description.

**D2. Additional packages.** Two workspaces are added to the spec's tree:

- `packages/storage-s3` (`@hostmark/storage-s3`): the `aws4fetch` `ObjectStorage` implementation, shared by
  every adapter on the S3 API. It is portable, so it does not belong in a single adapter, and it is not
  domain logic, so it does not belong in core.
- `adapters/local`: the docker compose adapter required by E0.

**D3. Runtime targets.** Docker images and `engines` target Node 22, because maintenance task M2 depends on
upgrading from it. Tests may run on a newer host Node.

**D4. Internal packages are consumed as TypeScript source.** Each `package.json` `exports` map points at
`./src/*.ts`. Adapters bundle with esbuild, Vite or wrangler. There is no per-package build step.
`tsc --noEmit` is typecheck only.

## HTTP surface

**D5. URL layout.** The spec mixes `/uploads` and `/api/files/:id`. Canonical paths are:

| Path                                                  | Notes              |
| ----------------------------------------------------- | ------------------ |
| `GET /api/health`, `GET /api/health/deep`             | public             |
| `POST /api/uploads`, `POST /api/uploads/:id/complete` | authenticated      |
| `GET /api/files`, `GET/PATCH/DELETE /api/files/:id`   | authenticated      |
| `GET /api/files/:id/events`                           | authenticated, SSE |
| `GET /api/stats`                                      | authenticated      |
| `POST /api/debug/cpu?ms=`                             | admin only         |
| `POST /api/rum`                                       | public, see D18    |
| `/api/auth/*`                                         | Better Auth        |
| `GET /api/openapi.json`                               | generated document |
| `GET /f/:id`, `GET /media/:id/:size.webp`             | public, see D6     |

`PATCH /api/files/:id` with `{ "isPublic": boolean }` is new: the spec has an `is_public` column and no way
to set it.

**D6. Thumbnails.** Public thumbnails use `GET /media/:id/:size.webp`, which streams the variant through api
with `Cache-Control: public, max-age=31536000, immutable`, so the CDN caches it. It responds only for files
that are `ready`, public and not deleted; otherwise 404. The bucket stays private. The private panel uses
presigned GET URLs from the API.

Consequence: after a file is unpublished or deleted, the origin returns 404, but copies already on a CDN or in a
browser survive for up to a year, because `immutable` means they are never revalidated. Nothing purges them yet:
E3 adds a CDN purge on both paths, and a browser copy cannot be recalled at all. Neither unpublishing nor deleting
is an instant takedown.

**D7. Authentication and ownership.** A request is authenticated by a `Bearer` API key or a Better Auth
session cookie, resolving to a principal `{ userId, apiKeyId | null, isAdmin }`. Sessions have
`isAdmin = false`. The owner of a file is the user, so 404 checks, listing and deduplication are all per
user, never per key. The `files_key_created` index is dropped in favour of `files_user_created`.

Requests authenticated by cookie must pass a same-origin check on mutating methods (Hono `csrf()` or
equivalent, plus Better Auth `trustedOrigins`). Bearer requests skip it.

`AUTH_SIGNUP_ENABLED` controls registration. Deployed environments should disable it unless a run needs it,
because open signup plus public `/f/:id` pages is a free image host. Email verification is off.

**D8. Status codes beyond the spec.** 403 for a non-admin calling `/api/debug/cpu` or sending `x-chaos`; a
chaos test that silently did nothing would be worse than a loud failure. 503 from `/api/health/deep` when a
dependency is down. 429 is not implemented (it is optional).

**D9. Response headers.** `x-trace-id`, `x-platform` and `x-version` are set on every response produced by
api, including errors. Platform-served static files cannot carry them. When dependency resolution itself fails,
the 500 problem response still carries `x-trace-id` and the `x-platform` and `x-version` of the last successful
resolve (absent only if the very first request fails), and the failure is logged with `console.error`.
Every 401 also carries `WWW-Authenticate: Bearer` (RFC 9110).

**D10. Upload contract.** `POST /api/uploads` takes `{ contentType, bytes }` and returns
`{ fileId, uploadUrl, uploadHeaders, expiresAt }`.

- `contentType` not in the allowed list is 400; `bytes` above 10 MiB (10 485 760) is 413.
- A signed `Content-Length` pins the exact size, so the declared `bytes` value is signed and the client must
  PUT exactly that many bytes with exactly `uploadHeaders`. The `bytes` parameter of `presignPut` is
  therefore the exact length.
- `complete`: no object is 409; object above the limit is deleted and returns 413 (this covers platforms that
  ignore signed length); otherwise `files.bytes` is set from `head` and the status moves
  `pending_upload → queued`. If enqueueing fails, the status is reverted conditionally and the call returns
  503.

**D11. `/api/debug/cpu` cap.** `ms` is limited to 1..30000; anything else is 400.

**D12. `/api/stats`.** Reads the last 30 rows of `daily_stats` for the current platform. The spec's optional
stats service is not implemented.

## Data

**D13. Single initial migration.** The spec's `alter table` statements and the Better Auth tables are merged
into the first migration. The `user` table therefore exists from E0, even though login UI arrives in E1. `0001_files_api_key_set_null` followed it before the first release, when the seed rotation needed `files.api_key_id` to be `on delete set null`; `pnpm generate` names its output `initial`, so give later migrations an explicit `--name`. A deleted file keeps its row as a
tombstone (D19), so `uploads`, `ready` and `bytes_in` of daily-stats stay stable after a delete. `failed` is a
snapshot and may change when a failed file is deleted before a later recompute (D57).

Two columns are added to `files`:

- `last_activity_at timestamptz not null`: set on enqueue, requeue and processing start. Stuck detection needs
  it because `queued_at` must stay untouched: it anchors `upload_to_ready_ms`.
- `purged_at timestamptz`: set once objects are removed. `deleted` rows stay as tombstones so a same-day
  delete does not distort `uploads`, `ready` and `bytes_in` of `daily_stats` (not `failed`, see D57), and cleanup can tell what still needs purging.

**D14. Seed.** `api_keys.user_id` is `NOT NULL`, so the seed creates users first. Key values come from
`SEED_API_KEY` and `SEED_ADMIN_API_KEY`. A value that is set is the only key of its seed user afterwards
(rotation, D75). A value that is unset keeps the existing key of that user and generates nothing; only a user
without any key gets a generated key, printed once. Key values are never committed.

**D15. Storage keys** use `userId`, because `api_key_id` is nullable:

```
originals/{userId}/{fileId}
variants/{userId}/{fileId}/{size}.webp
```

**D16. Variants.** Every `ready` file has exactly three variants, labelled 128, 512 and 1600. A label is the
maximum longer side, and images are never upscaled, so a 300 px source produces `512` and `1600` variants at
300 px. That keeps `/media/:id/512.webp` valid for every ready file. Skipping sizes would leave small images
with no variant at all.

EXIF orientation must be applied to the pixels before re-encoding. Stripping the tag without rotating yields
wrongly oriented thumbnails. Originals keep their EXIF but are never served publicly.

## Queue, worker, scheduler

**D17. Port changes.** Compared to the spec:

```ts
export interface JobContext {
  attempt: number; // 1..maxAttempts, as the platform counts it; it can lag or restart (D63), so core's own bound is files.attempts (D72)
  maxAttempts: number;
  receivedAt: Date;
  crash(): Promise<never>; // chaos=crash; Node: process.exit, Workers: throw without ack
}

export interface Queue {
  send(msg: JobMessage, opts?: { delaySeconds?: number }): Promise<void>;
  sendBatch(msgs: JobMessage[]): Promise<void>; // adapters chunk to platform limits
  ping?(): Promise<void>; // absent when the platform cannot ping; reported as "unknown"
}

export interface Clock {
  now(): Date;
  sleep(ms: number): Promise<void>; // chaos=slow; makes it testable
}
```

`ObjectStorage.get` on a large object is the only way to read variants, including for `/media`. `ImageProcessor`
is unchanged. `InvalidImageError` is exported from core and thrown by processors for undecodable input.

Worker rules that follow from platform differences:

- `chaos=crash` keys off `files.attempts === 1` after the step 1 increment, not `ctx.attempt`, so it behaves the
  same on every platform whatever its counter does for a job that died with its worker.
- `chaos=fail` throws every time.
- On `ctx.attempt >= ctx.maxAttempts` the handler sets `failed`, records `jobs_dead_lettered`, then rethrows so
  the platform moves the message to the DLQ. If only the file's own counter made the job final
  (`files.attempts >= MAX_ATTEMPTS` while `ctx.attempt` is lower) and the row was updated to `failed`, it returns: the row and
  `jobs_dead_lettered` are the record, no DLQ copy is written, as for a scheduler-driven `failed` (D55, D72).
- `InvalidImageError` sets `failed` and returns normally: no retry.
- Step 6 is conditional on `status = 'processing'`, so a delete racing the job cannot resurrect the file.

Shared constants in `@hostmark/contract`: `MAX_ATTEMPTS = 5`, `BACKOFF_SECONDS = [10, 30, 90, 270]`,
`VARIANT_SIZES = [128, 512, 1600]`, `MAX_UPLOAD_BYTES`, `ALLOWED_CONTENT_TYPES`, TTLs.

**D19. Scheduler touches only the database and the queue,** as the architecture diagram shows; it has no
storage access.

- `cleanup-expired` marks expired files and `pending_upload` rows older than 1 h as `deleted`, then enqueues
  `delete_file` for `status = 'deleted' and purged_at is null`.
- The worker's `delete_file` handler removes the original and all three deterministic variant keys, deletes
  `file_variants` rows and sets `purged_at`. It computes keys rather than reading `file_variants`, so it also
  catches objects from an interrupted `process_image`.
- `requeue-stuck` claims rows with a conditional `update ... set last_activity_at = now() where
  last_activity_at < cutoff returning id`, so a double run claims each row once, then sends new messages. Rows
  with `attempts >= MAX_ATTEMPTS` become `failed` instead: otherwise a job that kills its worker loops forever.
- `daily-stats` upserts, so reruns are harmless.

Each query is bounded (1000 rows per run). The next run picks up the rest.

**D20. SSE.** `GET /api/files/:id/events` polls the database every second, because services do not call each
other. It emits a `status` event on change, closes on a terminal status, and closes after 60 s at most. The
client reconnects, and falls back to polling every 2 s if SSE fails. The server span and `http.server.request.duration`
of this route cover the setup only, not the stream, because the response is returned when the stream starts.

## Frontend

**D21. Pages.** `packages/pages` prerenders `/` and `/pricing` at build time, and `/f/:id` is rendered by api.
The SPA shell is built to `app/index.html`, with `/login`, `/signup`, `/app` and `/app/*` rewritten to it.
`apps/web/dist` is the single static directory that adapters serve. The local adapter serves it with the same
`Cache-Control` rules as a CDN so behaviour matches.

## Telemetry

**D18. `/api/rum`.** Public because landing page visitors have no session. Body size is limited, and every
attribute is validated against a closed list so that hostile input cannot create unbounded metric cardinality.

**D22. Telemetry boundary.** `packages/core` depends only on `@opentelemetry/api` and the helpers in
`@hostmark/telemetry`. Providers are installed by adapters: `@hostmark/telemetry/node` for Node, and whatever
current Cloudflare documentation recommends for Workers (decided in E3). Locally, `grafana/otel-lgtm` runs in
compose.

## Load testing

**D23. Tools.** k6 runs from the `grafana/k6` Docker image because it is not installed on the host and CI needs
the same image. Browser scenarios S10 and S13 use Playwright.

## Foundation details

**D24. Contract details left open by the spec.**

- Route definitions in `@hostmark/contract` use full paths including `/api` (`createRoute` path `/api/files/{id}`), so core registers them on an app without a base path. `GET /f/:id` and `GET /media/...` are not JSON and have no route definition.
- Success codes: `POST /api/uploads` is 201, `complete` is 200 and returns the file, `DELETE` and `POST /api/rum` are 204.
- `CreateUploadRequest.bytes` has no schema maximum: above 10 MiB the answer is 413 (D10), which a schema failure (400) would hide. This includes values beyond `Number.MAX_SAFE_INTEGER`: the schema is `positive().multipleOf(1)` rather than `int()`, because `int()` rejects unsafe integers with a 400.
- `GET /api/files` returns `{ items, nextCursor }`; `limit` is 1..100, default 50; the cursor is the last returned file id and opaque to clients. File objects carry presigned variant URLs in both list and detail.
- `POST /api/rum` takes one metric `{ name, value, rating?, platform, variant, topology, region }`. All string attributes come from closed lists in `constants.ts` (`RUM_*`); unknown keys are rejected (D18).
- RFC 9457 `type` defaults to `about:blank`; `Problem` also allows an `errors` array for 400 field details.
- The typed client lives at `@hostmark/contract/client` (also re-exported from the main entry). It parses responses with the schemas and throws `ApiError` carrying the problem document; `deepHealth()` resolves for 503.

**D25. Database details.**

- Columns are snake_case, properties camelCase. Better Auth tables keep the property names its Drizzle adapter looks up (`user`, `session`, `account`, `verification`).
- Two partial indexes beyond the spec back the scheduler queries of D19: `files_activity` (stuck detection) and `files_unpurged` (purge). `files_user_created` is `(user_id, id desc nulls first)`, matching a plain `order by id desc`.
- `Database` is `PgDatabase<PgQueryResultHKT, typeof schema>`; a compile-time test proves postgres-js and Neon databases, and their transactions, are assignable to it. The main entry of `@hostmark/db` imports no driver; `@hostmark/db/node` holds the `postgres` helpers (`createNodeDb`, `migrate`).
- `apiKeyHash` helpers (`hashApiKey`, `generateApiKey`) live in `@hostmark/db` so seed and core share one SHA-256 implementation (Web Crypto).
- The seed users `seed-user` and `seed-admin` have no credentials and cannot log in.

**D26. Core entry points.** `@hostmark/core/ports` has no runtime dependency except the dependency-free `InvalidImageError`, so `packages/image` and `packages/storage-s3` depend on it without pulling in core. `DomainError` subclasses carry `status`, `code` and `title`; `InvalidImageError` maps to 422.

**D30. WASM image processor.** `@hostmark/image` takes an injected `WasmLoader` that returns compiled `WebAssembly.Module`s, because Workers cannot compile WASM from bytes at runtime. The Node loader is `@hostmark/image/node`; the main entry imports no `node:*`. Codecs are initialised lazily and reused, but an instance that threw is dropped and created again from the compiled module: a libjpeg error exit or a Rust panic leaves wasm memory unusable (or leaking), and one bad upload must not damage the next. Calls into one codec are serialised for that reason. The PNG decoder is a vendored copy of the wasm-bindgen glue of `@jsquash/png` with per-instance state (`src/png.ts`), because the package keeps its instance and heap in module-level variables and cannot be re-initialised after a panic. Only errors that the input can cause (`ExitStatus`, `Decoding error`, a PNG decode panic) become `InvalidImageError`; loader and runtime failures stay ordinary errors and are retried (D55). The WebP encoder ships SIMD and non-SIMD binaries, so the loader receives `simd` (from the same validation probe jSquash uses) and must return the matching module.

**D31. Pixel limit.** Input is rejected with `InvalidImageError` when the header (JPEG SOF, PNG IHDR, WebP VP8/VP8L/VP8X) claims more than 50 megapixels, before any decoding. The JPEG header walk follows libjpeg's marker rules (`FF 00`, fill bytes, standalone markers, a lone EOI before the frame header all handled alike), so the size it sees is the size the decoder will allocate. Decoded RGBA costs 4 bytes per pixel, so the limit alone does not fit Workers memory (about 128 MB, which holds roughly 12 to 16 MP with a resize buffer); the limit is a constructor option so the Workers adapter can lower it. Anything above it is a decompression bomb candidate: a 10 MB PNG can claim far more than it holds.

**D32. Resize before rotate.** Variants are resized from the unrotated pixels, then the small result is rotated by the EXIF orientation. The pixels equal the rotate-first order, but no full-size rotated copy is made. Sizes are processed largest first and each resize starts from the previous result. Reported `width` and `height` are the upright dimensions. Malformed EXIF is treated as orientation 1.

**D40. Telemetry helpers.** The main entry of `@hostmark/telemetry` imports only `@opentelemetry/api` and parses `traceparent` itself, so propagation does not depend on a registered propagator and an invalid header yields `undefined`. The worker span gets a link, not a parent, so it starts its own trace. `tracestate` is relayed only as the link attribute `tracestate.raw`, because building a `TraceState` needs `@opentelemetry/core`. The logger writes one JSON line per call (reserved keys win over caller fields), never throws, and `createTelemetry` is a no-op without providers. The logs API lives in `@opentelemetry/api` 1.10; `@opentelemetry/api-logs` is not used.

**D41. Node SDK bootstrap.** `startNodeTelemetry` returns `{ shutdown, write }`. `write` is the sink for `createTelemetry(service, { write })`: it prints the line and forwards it as an OTLP log record, so logs reach the backend with the active trace context. With an empty `otlpEndpoint` a no-op span processor is installed, because NodeSDK creates no tracer provider from an empty processor list, and empty metric readers and log processors stop it from falling back to `OTEL_*` environment defaults.

**D42. S3 storage.** `@hostmark/storage-s3` presigns with `AwsV4Signer` (`signQuery`, `allHeaders` for PUT), so `content-type` and `content-length` are part of the signature; MinIO enforces both (403 otherwise). Presigned URLs use `publicEndpoint`, server calls use `endpoint`. One retry on 5xx/429 instead of the aws4fetch default of 10, to keep hidden retries out of benchmark latency. `delete` sends single DELETEs, four at a time. Object keys are percent-encoded per segment before signing (aws4fetch turns a literal `+` in the path into a space), and `.`/`..` segments are rejected. `get` throws on `NoSuchBucket` instead of returning `null`.

**D50. Upload response.** `uploadHeaders` carries only `content-type`; the signed length is implied by the body. `expiresAt` in the create response is the expiry of the presigned URL (now + 600 s), not of the file (now + 7 days, stored in `files.expires_at`).

**D51. Cookie CSRF check.** Mutating requests authenticated by session cookie must carry an `Origin` whose host equals the first entry of `x-forwarded-host` (a proxy chain appends) or `host`, compared case-insensitively; otherwise 403. Bearer requests are exempt. Sessions are never admin.

**D52. Completing an upload.** The object is checked with `head` at `complete`. A missing object is 409. An object larger than `MAX_UPLOAD_BYTES` is deleted, the file is marked `failed` and the response is 413. If `queue.send` fails the file returns to `pending_upload` and the response is 503. The `x-chaos` admin check runs first, on the mere presence of the header, so a non-admin gets 403 before validation or anything else happens (same for `/api/debug/*`, D8).

**D53. Pagination cursor.** The `cursor` of `GET /api/files` must be a UUID; anything else is a 400 problem response.

**D54. Worker steps.** `process_image` has the spans `claim`, `download`, `hash`, `dedup`, `transform`, `write_variants`, `commit`, `ack` (hash and dedup both belong to step 3). The commit is conditional on `status = 'processing'` and upserts `file_variants`. The commit transaction reports `committed`, `deleted` or `superseded`: when it affects no row it selects the status. Only `deleted` (a delete won the race) removes the variant objects the job wrote. `superseded` (the row is `ready` or `failed`: another delivery finished the file first, or `requeue-stuck` failed it) leaves the objects alone. For `ready` they are the same keys the winner uses. For `failed` they stay without `file_variants` rows until the purge removes them, which is bounded and accepted. A claim that misses on a `deleted` row also removes variants, covering objects written after `delete_file` ran (D74). Cleanup failures are not swallowed: the job fails and is retried. Dedup is per user: variants of an earlier ready file with the same hash are copied through `get`/`put`; if their objects are missing the job processes normally.

**D55. Failure bookkeeping.** `last_error` is written on every failed attempt. On the final attempt (`attempt >= maxAttempts`) the file becomes `failed`, `jobs_dead_lettered` is counted and the error is rethrown so the message reaches the DLQ; earlier attempts count `jobs_retried`. A job that is final only through `files.attempts >= MAX_ATTEMPTS` and updated the row records the failure and returns without rethrow and without a DLQ copy; when no row was updated (a delete won) it rethrows, and the retry acks on the claim miss (D17, D54, D72). `InvalidImageError` marks `failed` immediately and returns, so the message is acked without a retry or a dead-letter count.

**D56. Scheduler results.** `processed` of `cleanup-expired` is the number of `delete_file` messages enqueued (the number newly marked deleted is logged as `marked`). `processed` of `requeue-stuck` is requeued plus failed rows. Rows at `MAX_ATTEMPTS` are failed with `last_error` kept, or `gave up after 5 attempts` if empty, and counted in `jobs_dead_lettered`. A requeue resets `chaos` to `none` (D73). The metric attribute for the job name is `scheduler.job`. Claims use a conditional update that repeats the staleness test, so overlapping runs claim each row once.

**D57. daily-stats semantics.** Rows are cohorted by `created_at` within a UTC day. `uploads` counts files with `queued_at` set, `ready` those with `ready_at` set, `failed` those with `status = 'failed'` and `queued_at` set (so `failed <= uploads`), taken as a snapshot when the day is computed; `bytes_in` sums `bytes` of the uploads. Percentiles are of `ready_at - queued_at` in ms and are null for an empty day. The row is upserted per `(day, platform)`. Each run recomputes the previous two UTC days so late `ready_at` and failures are picked up, and the second pass can lower an earlier `failed` when the file was deleted meanwhile; `processed` of the run is the sum of `uploads` over those days.

**D58. createApp options.** `createApp(resolveDeps, { probeTimeoutMs })` takes an optional second argument; the default probe timeout for `/api/health/deep` is 2000 ms.

**D59. Contract suites.** `@hostmark/core/test/contract` exports `describeQueueContract`, `describeObjectStorageContract` and `describeImageProcessorContract`, each taking `(name, factory)`, and `webpDimensions` for adapters that check variant sizes themselves. The factory returns a harness: the queue one is `{ queue, receive(max, waitMs), consume?, close? }` (`receive` because delivery is platform specific), the storage one `{ storage, capabilities?, close? }`, the image one `{ processor, fixtures }` with `large` and `small`, and optional `withMetadata` and `rotated`. Optional parts are declared by the harness and shown as skipped tests when absent: `consume` (redelivery with attempt numbers, DLQ after `maxAttempts`) and `queue.ping` for queues, the three `capabilities` flags (`rejectsWrongLength`, `rejectsWrongContentType`, `expiresUrls`) for storage, which skip a test unless the flag is `true`, and the two optional image fixtures. Besides vitest the suites import only core's `InvalidImageError` and port types and the `JobMessage` type of `@hostmark/contract`, nothing platform specific.

**D60. Local runtime bundle.** Each service of `adapters/local` is one esbuild ESM bundle (`api`, `worker`, `scheduler`, `run-job`, `init-bucket`, `migrate`, `seed`) inside one Docker image. Only the four `@jsquash/*` packages stay external: they load their `.wasm` files relative to the module, so the runtime stage gets them from `pnpm deploy --prod --frozen-lockfile` at the locked versions (D68). The smoke test proves the wasm path inside the container.

**D61. Compose configuration.** `docker-compose.yml` reads `adapters/local/.env`, copied from the committed `.env.example` (local-only placeholders, never real secrets; D14 seed keys live there). All host ports bind to 127.0.0.1: api 58080, Postgres 55432, Redis 56379, MinIO 59000, Grafana 53000, OTLP/HTTP 54318. Presigned URLs use `S3_PUBLIC_ENDPOINT` (`http://127.0.0.1:59000`) because the host is part of the signature; the services use `S3_ENDPOINT` (`http://minio:9000`).

**D62. MinIO CORS.** The chainguard MinIO build answers the bucket CORS API with 501 NotImplemented. CORS is therefore set server-wide with `MINIO_API_CORS_ALLOW_ORIGIN=*` (verified: preflight for PUT with `Content-Type` is allowed). `init-bucket` still tries the bucket API first and logs the refusal. The lifecycle rules (`originals/` and `variants/` expire after 8 days, D74) are applied through the S3 API, which requires a `Content-MD5` header on this server.

**D63. BullMQ mapping.** `image-jobs` uses `attempts = MAX_ATTEMPTS` with a custom backoff strategy reading `BACKOFF_SECONDS`, `lockDuration` 60 s and no `jobId` (no deduplication, same as the other adapters). `ctx.attempt = max(job.attemptsStarted, job.attemptsMade + 1)`: BullMQ's `attemptsMade` counts only finished attempts, so a stalled attempt (worker died, lock expired) would be invisible, while `attemptsStarted` counts every start and tracks core's `attempts` column (claim) for a single message, which is why the crash smoke step ends with 2 attempts. The worker sets `maxStartedAttempts = MAX_ATTEMPTS` (a job that keeps killing its worker is failed after five starts) and `maxStalledCount = MAX_ATTEMPTS` (BullMQ's default of 1 failed a job after its second stall with `attemptsMade` still 1). The attempt that is the last by this count fails with `UnrecoverableError`, so BullMQ does not schedule a sixth start whatever `attemptsMade` says. The producer connection has no offline queue and one retry per command, and `send` gives up after 5 s, so a Redis outage makes `complete` answer 503 (D52) instead of hanging. `delaySeconds` is the job `delay`; `sendBatch` is `addBulk` in chunks of 100.

**D64. Dead-letter queue on BullMQ.** BullMQ has no native DLQ. The worker's `failed` listener copies the payload to the queue `image-jobs-dlq` when the job has `finishedOn`, which BullMQ sets only on terminal failure (exhausted attempts, `UnrecoverableError`, too many stalls or starts). A copy gated on `attemptsMade` missed jobs failed by the stall check. If the fifth start kills the process before core can mark the row, BullMQ fails the job on the next pickup and `requeue-stuck` marks the row `failed` (it has `attempts >= MAX_ATTEMPTS`). The copy is a second step: if the process dies between BullMQ's `moveToFailed` and the DLQ write, the job stays in BullMQ's failed set (kept 7 days) with no DLQ entry, and nothing reconciles it; the file row is still marked `failed` by `requeue-stuck`. A job that keeps killing its worker (poison input, out of memory) takes the other jobs in flight with it each time: they stall too and each loses one start, so an innocent sibling that runs longer than the killer can use up its five starts next to it. `close()` waits for pending copies. `InvalidImageError` returns without retry (D55) and is not dead-lettered.

**D65. Crash recovery latency.** `ctx.crash` is `process.exit(1)`; the worker service has `restart: unless-stopped`. A job held by the killed process is taken back by BullMQ's stalled check (lock 60 s, check every 30 s), so the file becomes `ready` roughly 60 to 90 s after the crash. This is a property of BullMQ, not a defect to fix. Each further crash of the same job costs the same again; after five starts the job is dead-lettered (D63, D64).

**D66. Retry scale for tests.** `QUEUE_BACKOFF_SCALE` (default 1) multiplies the backoff delays. The smoke test recreates the worker with `0.02` so five attempts finish in seconds, then restores the default.

**D67. Scheduler process.** `croner` runs `createSchedulerJobs` in UTC with `protect: true` (no overlap inside one process) and `catch`; cross-process safety remains the database claim of D19/D56. `run-job.js <job>` executes one job and exits, for verification and manual use.

**D68. Docker build.** The build stage uses pnpm 12 with the allowlist of D201, like every other install (the earlier `pnpm_config_strict_dep_builds=false`, which ignored the scripts of esbuild, msgpackr-extract and protobufjs, is gone). The lockfile holds two releases younger than pnpm 12's default `minimumReleaseAge`; they are named in `minimumReleaseAgeExclude` of `pnpm-workspace.yaml` (`bullmq@6.5.3`, `set-cookie-parser@3.2.2`) instead of switching the check off. Drop the entries once a later bump moves past them. The runtime stage gets its `node_modules` from `pnpm deploy --prod --frozen-lockfile`, so it holds exactly the jSquash packages (the only external dependencies of the bundles, kept so the Node loader finds their `.wasm` files) at the locked versions, with no `npm install` and no unlocked resolution. The `# syntax=` directive is omitted because it needs Docker Hub access at build time. `APP_VERSION` is a build argument (the commit) and becomes `service.version` and `x-version`.

**D69. Local test layout.** The image contract runs always (it needs no service). The storage contract runs when `S3_TEST_ENDPOINT` is set, the queue contract when `REDIS_TEST_URL` is set; otherwise they are skipped. The queue harness reads with `startConsumer`. Trace linking is verified by the smoke test through the Grafana proxy to Tempo: producer and worker are two traces joined by a span link (D40), so criterion 3 is met as "linked", not as one parented tree.

## Platforms

**D70. Platform opt-in.** Every platform adapter lives in the repository and is off by default. `platforms.json` at the repository root lists each platform with `enabled`, its adapter directory, a `status` of `emulated` or `deployed`, and the names of its required secrets, never their values. Every platform starts with `enabled: false`. `pnpm platform list` shows the state, `pnpm platform check <name>` reports missing variables without printing values, and `pnpm platform deploy <name>` refuses unless the platform is enabled. The GitHub Actions deploy workflow runs only on `workflow_dispatch` and builds its matrix from enabled entries, so a merge to `main` deploys nothing. Disabled adapters still go through typecheck, lint and emulator tests in CI, so they do not rot.

**D71. Scope extension.** The owner extended the current effort to the portable variant of all seven platforms: Cloudflare, Google Cloud, AWS, Railway, Fly.io, Vercel and VPS. Idiomatic variants (E9), multi-region (E8) and the preview and rollback pipeline (E4) stay later: they depend on portable adapters that have run on the real platforms. Enabling a platform and deploying it are the owner's decisions, made per platform, because each one needs an account and costs money.

**D72. Stored errors.** `files.last_error` holds a generic `processing failed` for unexpected errors; only `InvalidImageError` messages and the deliberate chaos and missing-original messages are stored verbatim. The raw error goes to the log with the trace id. Stored text is shown to users, so internals must not leak into it. A job also treats `claimed.attempts >= MAX_ATTEMPTS` as final, because a platform counter can restart when a message is requeued (D63) and the file's own counter then bounds the retries. When that is the only reason it is final and the row was updated, the job records the failure and returns instead of rethrowing (without an updated row it rethrows, so a failed cleanup of a deleted file is retried), so the platform spends no retry and no DLQ copy exists (D17, D55). `jobs_dead_lettered` is counted only for rows actually updated. Kills do not run the failure handler, so `files.attempts` can exceed five (up to nine was measured) until `requeue-stuck` fails the row.

**D73. Requeue clears chaos.** `requeue-stuck` sends the requeued message with `chaos: 'none'`. Chaos is a field of the queue message, not of the row, so a requeue starts from a clean message. A chaos request describes one injected failure; keeping it on a requeue would make a stuck job fail again by design and hide whether the recovery path works.

**D74. Variant cleanup safety net.** Variants written by a job that lost the race are removed by the commit that finds the file `deleted`, and those written after `delete_file` ran by the claim miss (D54). As a second line of defence the bucket lifecycle rule that expires `originals/` after 8 days also covers `variants/`, so a leak that survives even the retry ends in expiry rather than in permanent storage cost. A lifecycle rule goes by object age and cannot see the database, so this is safe only because `expires_at` is set once, at creation, to 7 days: an object older than 8 days always belongs to an expired file. Anything that lengthens retention or lets a file outlive `FILE_RETENTION_DAYS` must move this rule first, on every adapter, or it deletes live thumbnails. The adapter owns the rule.

**D75. Seed key rotation.** The seed reads `SEED_API_KEY` and `SEED_ADMIN_API_KEY` (D14); when both are set they must differ, otherwise it refuses. A value that is set rotates: all other keys of that seed user are deleted, including keys added by hand, because the seed owns those two users. Their files are kept with `api_key_id` set to null (`files.api_key_id` is `on delete set null`, so a rotation during an upload cannot abort). A value that is unset keeps an existing key of that user and generates nothing only when one exists (a user without a key gets a generated one), so two runs without values leave the first keys working. Re-seeding also updates `is_admin`, `name` and the owning user of an existing key hash.

**D76. Periodic re-send of `queued` rows.** `requeue-stuck` runs every five minutes and re-sends rows that have been `queued` longer than the stuck threshold of ten minutes. During a long backlog this repeats messages for rows that are merely waiting. This is accepted: the conditional claim keeps a duplicate from corrupting a row (D54), and suppressing duplicates would need a per-row send timestamp that every adapter would have to maintain. Duplicates are not free: every start increments `files.attempts`, so duplicates share the five-attempt budget and a file can reach `failed` without the full backoff ladder. Measured with one 50 MP file and 0, 3 and 6 re-sends (`load/tools/behaviours.mjs abandoned-send`): a duplicate that finds the row already claimed or `ready` is skipped without touching `attempts`, so only duplicates that start while the first one is processing count. `attempts` stayed 1 on one process with one job, and rose to the number of job slots (2 with two processes, 4 with one process at concurrency 4), never above it however many re-sends there were; each file was processed to completion once.

**D77. Truncated JPEGs.** A JPEG cut off inside its scan data is accepted: libjpeg recovers the rows it has and fills the rest, as browsers show it, and the file is processed from that. A file cut before the scan, or with a broken table, is refused as `InvalidImageError`. A truncated PNG or WebP is refused (their decoders do not recover).

**D78. CMYK and YCCK JPEGs.** A JPEG with four colour components (CMYK, YCCK, usually Adobe) is refused with `InvalidImageError` before any decoder runs. The decoder cannot convert it to RGB (it exits with an error that used to damage the codec instance), and a dependable ICC-free conversion is out of scope for a benchmark app. Grayscale and three-component files are accepted.

**D79. Worker memory limit.** The worker service has `mem_limit: 4g` and the same `memswap_limit`, so the result does not depend on the swap of the host. Measured on the stack without swap, with maximum-size inputs (50 MP JPEG, 16-bit PNG, WebP, tall PNG) at concurrency 4 (the default until D97): one 50 MP job peaks at 1.9 GB; four at once at 2.3 GB (JPEGs) and 3.4 GB (mixed formats); a sustained stream of 24 such jobs peaked at 3.7 GB, with no kernel kill and every file `ready` on its first attempt. Lower figures in earlier runs (12 MP 0.75 GB, 24 MP 1.6 GB, 48 MP 2.7 GB, 3.5 GB limit) were for one job or a batch only; the 3.5 GB limit held a sustained stream only with 352 MB of swap. At concurrency 4 the margin above the sustained peak is about 300 MB, so more concurrency or a higher pixel limit needs a new measurement. Re-measured with the default of D97 (concurrency 1, two processes, `mem_limit: 4g` each) by the load tests, from the cgroup `memory.peak` of freshly restarted workers: the S9 stream of 24 maximum-size inputs (6 each of the four formats) peaked at 3.0 to 3.2 GiB per process in six runs, with one or two replicas, and a stream of 72 files on one replica stayed at 3.2 GiB, so the peak is a plateau and one process taking the whole stream is no worse; an earlier run gave 2.1 and 2.7 GiB and its cause was not established. There was no restart, no OOM kill and every file was `ready` on its first attempt. S4 and S5 (12 MP JPEGs) peaked at about 0.7 GiB per process. The margin to the limit is about 0.8 GiB per process. If the limit is reached, the kernel kills the worker (exit 137): the jobs in flight stall, are started again after the lock expires (D65) and are dead-lettered after five starts (D63, D64); a benchmark run that sees this measures retries, not the platform. Platforms with a smaller memory budget must lower the pixel limit or the concurrency instead (D31).

**D80. Session authentication.** `packages/auth` exports `createAuth({ db, secret, baseUrl, trustedOrigins, signupEnabled })`, which returns the `SessionAuth` port. It is Better Auth over the existing tables through its Drizzle adapter: email and password only, verification off (D7), sessions in Postgres, an `HttpOnly`, `SameSite=Lax` cookie that is `Secure` exactly when `baseUrl` is https, and no Node-only import. `signupEnabled: false` sets `disableSignUp`; existing accounts still log in. `seed@hostmark.test` and `admin@hostmark.test` cannot be registered, however they are spelled in case or surrounding whitespace: a real account with one of them would make every later seed fail on the unique email, and the seed must never adopt it, because that would hand out the admin role. The check runs in Better Auth's `databaseHooks.user.create.before`, so it holds for every route that creates a user, not only `/sign-up/email`. The two emails, `RESERVED_EMAILS` and `isReservedEmail` live in `packages/db` (`seed.ts`), the one source the seed uses too. The rate limiter never runs on a key a client can choose or that everyone shares. Better Auth keys it on `x-forwarded-for`, which a client can forge, and falls back to one shared `no-trusted-ip` bucket when the header is missing or holds a list: with the defaults, three wrong sign-ins from anyone locked every client out, and a rotating forged header was never limited. So `createAuth` takes an optional `clientIpHeader`. Set, it is the only header read (`advanced.ipAddress.ipAddressHeaders`), the limiter is on in every environment (3 attempts per 10 s on each of sign-in and sign-up, 100 requests per 10 s on any other path, per address), and an auth request whose header does not hold exactly one valid address is refused with 400 instead of being pooled into the shared bucket. Unset, the limiter is off (`rateLimit.enabled: false`): no trusted address means no limiter, and a burst gets no 429. Each deployed adapter sets `clientIpHeader` to a header its platform overwrites on every request before it is public (plan E3, E5 and E7); the local adapter leaves it unset. The counters are in memory, so the limit is per instance, and a load test must not use sign-in as a load path while the limiter is on. `trustedOrigins` entries are normalised with `new URL(entry).origin` and startup fails for one that is not an http(s) URL (`spa.test` is refused, `http://spa.test/` works). They pass Better Auth's own origin check on `/api/auth/*` only, not the same-origin check on API mutations (D51), and Better Auth checks any request that carries a cookie, `Origin` or `Referer`; a request with none of them passes. The auth route has a 64 KiB body limit, answering the same 413 as `/api/rum`, because sign-up is anonymous and stored a 30 MiB `name` before.

**D81. Public pages.** `packages/pages` holds pure functions that return HTML strings with Hono JSX and import no database or platform code: `renderLanding`, `renderPricing`, `renderPublicFile`, `renderNotFound`, `renderError`. The CSS is inlined (no stylesheet request), system fonts, one accent colour, no gradients, and the LCP element is the `h1` text on the landing and pricing pages and the image on `/f/:id`, so the text does not wait for JavaScript. Every page ends with `<script type="module" src="/rum.js" data-rum="" data-platform data-variant data-topology data-region>`; Hono writes the bare `data-rum` as `data-rum=""`, which is the same attribute in HTML. The values come from the closed `RUM_*` lists. `scripts/prerender.ts` writes `apps/web/dist/index.html` and `pricing/index.html` after the Vite build from `HOSTMARK_PLATFORM` (default `local`), `HOSTMARK_VARIANT`, `HOSTMARK_TOPOLOGY` and `HOSTMARK_REGION`, refuses a value outside the lists, and takes `HOSTMARK_DIST` as an alternative output directory. The contract is only a dev dependency, for the script and the tests, so the renderers stay free of it. Pricing shows example tiers and says so. Files have no stored name (the schema has no `original_name`), so the page title is generated from the dimensions; there is no user-controlled text on the page, but the renderers escape their input regardless and the tests feed them hostile strings.

**D82. `/f/:id` origin and caching.** Absolute URLs (`og:url`, `og:image`, canonical) are built from `AppConfig.publicUrl`, never from the request, when it is set, and then the page is sent with `Cache-Control: s-maxage=60, stale-while-revalidate=600`. A CDN keys that page by path, so building URLs from `Host` or `X-Forwarded-Host` would let one request with a hostile host plant a page that points every crawler at an attacker. Without `publicUrl` the origin comes from the first `x-forwarded-host` entry, else `host` (as in D51), and `x-forwarded-proto`; a host that is not a plain hostname with an optional port yields a page without absolute URLs; and the response is `private, no-store`. Deployed platforms must set `PUBLIC_URL`, and it should be the same value as the auth base URL. The page also sends a strict `Content-Security-Policy` (own origin only, inline styles, no frames), `nosniff` and `referrer-policy: same-origin`. Visibility is the rule of D6 (`ready`, public, not deleted). Consequence: after unpublishing or deleting, the origin answers 404 at once, but the page itself can still be served from a shared cache for up to 11 minutes (60 s fresh plus 600 s stale-while-revalidate); the images it points to follow D6 and can live far longer. `AppConfig` gains `publicUrl` and `rum` (partial overrides of the RUM attributes). The RUM platform and variant default from the platform key (`aws-portable` gives `aws` and `portable`); a value outside the closed lists falls back to `local`, `portable`, `single`, `local` instead of failing the request.

**D83. Failure handling of `/f/*`.** A missing, private, unfinished, deleted or malformed id, and any unmatched path below `/f/`, answers an HTML 404 from `packages/pages`; an unexpected error answers an HTML 500 with a generic message and logs the cause with the trace id, like the JSON routes. Every non-200 answer under `/f/` carries `Cache-Control: no-store`, including the 500 for a failed dependency resolution, which has no configuration to render with and stays a JSON problem document. The D9 headers are on all of them, and the route is recorded by its pattern `/f/:id`.

**D84. Cookie path verified.** With the real `createApp` and the real `createAuth` over Postgres, a session cookie runs upload, complete, get, list, patch, delete and the SSE stream of its own files (another user's file is a 404). Mutations without an `Origin`, with a foreign or lookalike one, or `null` get 403, while the host in `x-forwarded-host` is accepted and reads are not checked; Bearer requests skip the check and a bad Bearer is not rescued by a cookie. A session is never admin: `/api/debug/*` and `x-chaos` answer 403. No change to the ports was needed. Better Auth runs its own origin check on `/api/auth/*`, against `baseUrl` and `trustedOrigins`, so a dev setup that reaches the app through another host must list that origin. The session cookie is `better-auth.session_token`, with the `__Secure-` prefix over https. Packages that import `@hostmark/core` now typecheck its JSX dependency, so their tsconfig needs `"jsx": "react-jsx"` and `"jsxImportSource": "hono/jsx"`.

**D85. RUM script and build.** `src/rum.ts` is a second Vite entry written to the fixed path `dist/rum.js` and has no React. Hashed chunks would break a cached `rum.js` after a deploy, so the constants it imports are inlined into the file (it is self-contained, about 3.6 KB gzipped). It finds its tag with `document.querySelector('script[data-rum]')`, because a module script has no `document.currentScript`. It sends nothing unless `platform`, `variant`, `topology` and `region` are all present and in the closed `RUM_*` lists. Each metric goes in one request through `navigator.sendBeacon` with a `Blob` typed `application/json` (a string would be sent as `text/plain`), or through `fetch` with `keepalive` when `sendBeacon` refuses. The SPA shell gets the same tag from a Vite plugin after HTML processing, with values from `HOSTMARK_PLATFORM`, `HOSTMARK_VARIANT`, `HOSTMARK_TOPOLOGY` and `HOSTMARK_REGION` at build time, defaulting to `local`, `portable`, `single`, `local`. `@hostmark/contract` exports `./constants` so that the script can import the lists without pulling in zod.

**D86. Panel authentication and uploads.** The panel calls Better Auth with plain `fetch` (`sign-in/email`, `sign-up/email`, `sign-out`, `get-session`), not its client. Better Auth requires a `name` at signup, so the panel sends the part of the email before the `@`. Signed-out visits to `/app/*` redirect to `/login` through the session query in the router guard, and so does a 401 from any query, mutation or API call of an upload: one handler (`signedOut` in `session.ts`) removes every cached query except the session, sets the session to `null` and goes to `/login`. Uploads bypass the query cache, so `UploadError` marks a 401 from create or complete and the upload list calls the handler itself; any other upload error, including a refused PUT to storage, keeps its row and Retry. A session can also end with no 401 (the guard reads `null` when the cached session goes stale), so signing in removes the same queries, and the next user of the tab sees nothing of the previous one on either path. Every `fetch` to the API (the contract client and the Better Auth calls) carries a fresh `traceparent`, so the trace starts in the browser. `EventSource` cannot set headers, so the event stream and the PUT to storage carry none. The PUT to the presigned URL uses `XMLHttpRequest` (progress) with exactly `uploadHeaders` and no other header, so it adds no CORS preflight beyond what storage allows for that `Content-Type` (D62). A cancelled upload aborts the PUT and leaves its `pending_upload` row to the cleanup of D19; the client sends no DELETE. The gallery does not show `pending_upload` rows (a running upload is in the upload list above it), so a page may hold fewer tiles than rows, and "Load more" stays while a next page exists. Deduplication is invisible to the API (the worker does it, D54), so the gallery only marks a file as a duplicate when its `sha256` equals that of an older file in the loaded pages.

**D87. Live status and gallery polling.** The file page opens one `EventSource` once the file is known to be non-terminal, and closes it on a terminal event and on unmount. It falls back to polling every 2 s (`SSE_FALLBACK_POLL_MS`) when the browser gives up on the stream, after 3 consecutive errors without a successful open, or when no response headers arrive within 10 s (a buffering proxy). A close by the server's 60 s limit is an ordinary error followed by the browser's own reconnect, so it does not trigger the fallback. The page shows which of the two modes is active. The gallery never opens a stream per item, because browsers allow about six connections per host on HTTP/1.1: it refetches the list every 2 s only while a loaded file is `queued` or `processing`. The file page stops polling once its query is in error (for example 404). The usage panel is titled "Platform usage" because `/api/stats` is platform-wide (D12). The preview on the file page carries `width` and `height` computed from the file's dimensions and the variant size the way the worker does (longer side `min(size, longest)`), so the image reserves its space and causes no layout shift. Presigned thumbnail URLs change on every fetch, so each thumbnail keeps the first URL it saw and the image does not reload on each poll.

**D88. Static serving from the api process (local adapter).** `adapters/local/src/static.ts` is a platform-neutral handler (`createStaticHandler({ root })`, GET and HEAD) that runs before the app and returns `null` on a miss, so 404 handling stays in core, except under `/assets/`, which answers a `no-store` 404 itself so a CDN cannot keep it. `/api`, `/f`, `/media` and `/health` are never answered by it. `/login`, `/signup`, `/app` and `/app/*` serve `app/index.html`, with one trailing slash accepted on all three; `/` and `/pricing` resolve to the prerendered `index.html` and `pricing/index.html`; any path with a dot segment, a backslash or a NUL is a miss, and so is a symlink that leaves the root. Headers match what a CDN would apply: `/assets/*` `public, max-age=31536000, immutable`, everything else (HTML and the unhashed `/rum.js`) `public, max-age=300`. Files are read once and kept in memory, because the directory is immutable for the life of an image. The local adapter does not compress: there is no `Content-Encoding`, so the app script of about 740 KB goes over the wire as about 740 KB where a CDN sends Brotli or gzip (about 205 KB gzip). On loopback this costs little, but LCP and the transfer sizes in Web Vitals from `local` are not comparable with CDN-fronted platforms for the first load of `/app`; the landing and pricing pages are small. The api needs `BETTER_AUTH_SECRET` (32+ characters) and `PUBLIC_URL`, and exits at startup without them (`PUBLIC_URL` must be http or https and only its origin is used; the secret is trimmed before the 32 character check, and the `.env.example` placeholder passes because the local stack runs on it); `AUTH_CLIENT_IP_HEADER` is unset locally, so the limiter is off (D80); the worker and scheduler do not build the auth. There is one image for all services, so the worker and scheduler images also carry `/app/web` unused (about 750 KB). Extracting a shared Node runtime in E5/E7 moves `static.ts` and the secret check as they are.

**D89. End-to-end test in a browser.** `apps/web/e2e` runs Playwright against the running compose stack (`pnpm --filter @hostmark/web e2e` where a browser launches). On this sandbox Chromium cannot start on the host (Mach port rendezvous is denied), so the suite runs in `mcr.microsoft.com/playwright:v1.64.1-noble` with `e2e/forward.mjs` forwarding `127.0.0.1:58080` and `:59000` to `host.docker.internal`; the presigned URLs are not changed for the test. The journey holds the PUT back for 1.5 s so the progress bar can be observed, and answers the first read of the file as `processing` so the page always opens the event stream (the worker finishes in about a second, which would otherwise make the stream race with the first load). The journey also fails on console errors, page errors, failed requests (except an event stream aborted because the page was left) and 4xx or 5xx answers; the other three specs provoke errors on purpose and fail on page errors only. Web Vitals are checked by leaving each page for real after a click and asserting that the page recorded `LCP` and `CLS` beacons (a `sendBeacon` Blob body is invisible to Playwright, so the page records the names in `localStorage`) and that every beacon Playwright could see got a 2xx (it reports only some of those that leave with the unloading document), on a prerendered page and on `/f/:id`, the only page with a CSP. The reserved seed email is refused by Better Auth as "already exists" because the seed user is a real row; the reserved-email hook is covered in `packages/auth`.

**D90. Load tests: layout, results and guard.** `load/` is not a workspace package and has no dependencies; `node load/run.mjs <S1..S15|all> [--short]` runs a scenario in the `grafana/k6:2.3.0` image (S10 and S13 in the Playwright image) and `load/README.md` lists every variable. Scenario code is the same for every variant: only `BASE_URL` and the keys change, labels (`REGION`, `TOPOLOGY`, `VARIANT`, `NOTE`) are inputs, and no scenario names a platform (the platform is whatever `x-platform` answers). Results are written to `load/results/` and are **gitignored** (only `.gitkeep` is tracked): they depend on the machine and the day, and a result worth keeping is quoted in the report that discusses it. Each carries date, commit, `treeSha`, `dirty`, the load parameters and a `load.deviations` list (D98); `load.mode` is `reduced` whenever one differs from the specification, so a short or shortened run is never mistaken for the full scenario. Fixtures (1 MB JPEG, 10 MB PNG, and the maximum-size inputs of D79: 50 MP JPEG, 16-bit PNG, tall PNG and WebP) are generated by `load/tools/fixtures.mjs` into the gitignored `load/fixtures/`. A `BASE_URL` that is not literal loopback is refused until `LOAD_ACK_REMOTE=<host>` names it, and S5 and S6 additionally need `LOAD_ACK_BUDGETS=yes`; the check runs in `run.mjs` and again at scenario init (`load/lib/guard.js`, tested by `node --test load/test/*.test.mjs`, a glob because Node 22 reads a directory argument as a module path). `127.0.0.1.example.com`, `0.0.0.0` and `127.1` are not loopback. Every threshold set has an error gate (failed requests, failed checks, and dropped iterations for arrival-rate scenarios) next to a latency bound that a variant can raise explicitly with `P95_MS`: the bound is a load parameter like the others, so a raised one is listed as a deviation and the run is `reduced`. A gate that fails exits 99.

**D91. Loopback forwarder.** Docker Desktop has no host network, so for a loopback target `run.mjs` starts a `hostmark-load-fwd-<pid>` sidecar (`load/tools/forward.mjs`) that forwards `127.0.0.1:58080` and `:59000` to `host.docker.internal` (D99 changes this when the compose network exists), and runs k6 and Playwright with `--network container:<sidecar>`. The presigned URLs are signed for `127.0.0.1:59000` and are used unchanged (as in D89). The forwarder is one more TCP copy in every local number. `HM_LOAD_NETWORK=host` uses the host network on Linux.

**D92. Reduced forms.** S7 as specified (gaps of 5, 15 and 60 minutes, 10 repeats each) takes about 13 hours and means nothing on a process that is never frozen, so `GAPS` and `REPEATS` are parameters and the local run uses seconds (`GAPS=5,15,60 REPEATS=3`), labelled reduced with the total silence recorded. S9 has a second phase beyond the specification: a stream of maximum-size inputs (the four formats of D79, about 49 to 50 MP each) sent back to back, because the worker's memory peak (D79) shows only under a sustained stream, not with five PNGs; it fails unless every planned upload was sent and every file reached `ready`. S14 on the local stack can rebuild and recreate the api with `HM_LOCAL_DEPLOY=1`; otherwise it only proves that `x-version` is served. S15 needs a purge API and a cache header, which the local stack has neither of: it writes a result with `status: skipped`, `passed: null`, `load.mode: skipped` and a `skipped.reason`, measures nothing, and the `run.mjs` summary prints SKIPPED. With `PURGE_URL` set it needs a cache `hit` before the purge, a 2xx purge response and a positive `miss` or `dynamic` state after it. S12 records `Cache-Control` as received (D82); without a CDN no cache status exists and the hit ratio is not measured.

**D93. Counting a run's files.** Scenarios that upload record the newest file of the key before the first request and count only files created after it (`window`), by status, attempts and `ready_at - queued_at`. `pending_upload` rows left by cancelled uploads stay until cleanup, so they are reported as their own number and are not part of the processed count; `daily_stats` includes them.

**D94. Local observer and independent checks.** Against the local stack `run.mjs` reads the compose project while a scenario runs (`load/tools/observe-local.mjs`: `docker stats` and `inspect` of every worker replica, the cgroup `memory.peak` of each (a high-water mark the kernel keeps, not a 3 s sample) after restarting the workers for the scenarios that report memory (S4, S5, S9), restarts and OOMKilled; Postgres for status, attempts and timing of the run's files) and adds it to the result as `local`. `load/tools/spotcheck.mjs` compares k6's request counts with the counters the api exports to Prometheus (the export interval means a settle time of about 80 s). `load/tools/behaviours.mjs abandoned-send | repeat-killer` reproduces, with the worker stopped or killed by `docker kill`, the two behaviours that a benchmark cannot see from outside (`files.attempts` after duplicate sends, D76; a repeat killer using its siblings' attempts, D64); the third (D79) is the S9 stream. `chaos=crash` fires only on the first attempt (D65), so repeated kills are `docker kill` while a sibling is processing.

**D95. Browser scenarios.** S10 and S13 are Playwright specs in `load/playwright` run in the Playwright image (Chromium does not launch on the macOS host, D89). The repository is mounted read-only; run.mjs copies the specs to a scratch directory in the container and links `node_modules` to `apps/web/node_modules`, so `load/` needs no dependency of its own. S13 signs up a user outside the timed part and times the login, upload, `ready` and gallery thumbnail; sign-in is driven through the form and is low volume because it is not a load path (D80). INP is approximated from Event Timing as the worst interaction on the single page app, which is not the Chrome definition.

**D96. Local worker capacity and S4.** A worker process decodes and resizes on one JS thread (the WASM codecs do not run in parallel), and the 4000x3000 1 MB fixture costs it about 0.75 s, so one process drains about 1.3 files per second whatever its concurrency setting. Measured on a fresh worker at concurrency 1, 4 and 8: 1.29, 1.32 and 1.31 files/s with the main thread at 97 to 99 %; two processes at concurrency 1: 2.49 files/s (D97). The first E2 run, one worker container with 4 slots, drained S5's 1000 files in 779 s from the start of the burst (1.28 files/s), and S4 as specified (2 rps for 5 min) built a backlog and failed (`upload_ok` 60.5 %, 90 dropped iterations, `upload_to_ready_ms` p95 57 s over the files that finished in time, 51 files still queued); the 4 slots were not the cause, the one thread was. That result was kept as evidence and thresholds were not loosened. Because a scenario's backlog delays the next, `run.mjs` waits up to 15 min for an idle queue before each upload scenario (the database queue locally, a poll of the key's newest files by API otherwise) and records the wait as `local.waitedForIdleQueueS`.

**D97. Node workers scale by process, with one job per process.** Measured (D96): throughput of one worker process is the same at concurrency 1, 4 and 8, because the WASM codecs run on one JS thread, and it doubles with a second process. So `WORKER_CONCURRENCY` has no throughput effect on a Node adapter; it only raises the memory of one process (D79) and the longest time the event loop is blocked while a lock is held (60 s lock, D65). The default is therefore 1, and `adapters/local` runs `WORKER_REPLICAS` (default 2) worker containers through `deploy.replicas`, each with `mem_limit: 4g`; every Node adapter (E5, E7) scales by the number of processes or instances, not by slots. This overrides the spec's M7 wording on worker concurrency and D79's default of 4. A concurrency above 1 stays configurable. D64's loss of a sibling's attempts needs several jobs in one process, so it cannot happen at concurrency 1: a killed replica takes only its own job. `load/tools/behaviours.mjs repeat-killer` still shows it at `CONCURRENCY=4`. The smoke test runs one replica (`--scale worker=1`) where it stops and restarts the worker, and returns to the compose replica count at the end.

**D98. Result identity, scoping and the guard.** A result carries `commit`, `treeSha` and `dirty`: `treeSha` is the git tree of the working copy as it would be committed (HEAD plus changes plus untracked files that are not ignored), computed in a temporary index (`load/tools/tree.mjs`; the real index is not touched), and `dirty` means it differs from `HEAD^{tree}`, so a result names the code it ran and a committed tree gives the same value. Error gates and the headline read the `{scenario:X}` sub-metrics, so the warm-up requests of `setup()` are not part of a verdict. A scenario that has nothing to measure (S15 without a purge API) is `status: skipped`, not passed. `meaning` strings describe the local stack and are written only for a loopback target; a remote target must set `REGION` and `VARIANT`. `PURGE_URL` carries a token and is held to the target's rule: with a loopback target it must be loopback; with a remote one it must be the target's own host or be named in `LOAD_ACK_PURGE_HOST`. A presigned upload URL is checked at the request (`putObject`), so every path that uploads is covered. `upload_to_ready_ms` has a sample only for files that were terminal within the wait timeout; the result lists the timed-out count next to it and the database window (`local.db`) covers every file. A run during which the host stopped (a laptop on battery with the lid closed freezes Docker and `run.mjs` together) measures the sleep: a watcher process (`load/tools/pause-watch.mjs`, separate so that no blocking call in the runner can delay it) ticks every second and reports gaps above 5 s. Every result carries `host: {watcher, pauses, pausedS, keepAwake}`; a pause, or a watcher that does not report, makes the result `invalid` (`passed: null`, exit 3), and such a run is repeated. On macOS `run.mjs` also starts `caffeinate -i`, which does not stop a closed lid from sleeping the host. The watcher compares wall-clock ticks in its own process, so it misses a gap under 5 s or a freeze of the Docker VM alone; a clock step gives a false `invalid`, which is the safe side. The worker restart and idle wait before a scenario, the smoke test and `behaviours.mjs` are outside it.

**D99. Load path: the sidecar reaches a running stack over its compose network.** On Docker Desktop the path from a container to a published host port (`host.docker.internal:58080`) blocks a connection's 5-tuple for about 60 s after the server closed it first, so a new SYN that reuses that source port is dropped and the connection is made only on a SYN retransmission (delays of 3, 19, 36 and 68 s). This is what S4 of the second full run saw as 60 s hung requests: 17 `POST /api/uploads` calls with k6's 60 s timeout and 17 `pending_upload` rows created about 68 s late; in an earlier run with two such requests the api's own p99 for the route was 22 ms. It is neither the application nor host sleep. The S6 seed PUT that timed out at 17:47 CET is likely the same, not proven. The condition tested is a close by the server; a client-first close is safe in practice but not proven immune, and who holds the 5-tuple inside Docker Desktop is not known. The forwarder (`load/tools/forward.mjs`) therefore does not go through the published port when the stack's network exists: `run.mjs` starts the sidecar on `<project>_default` (`HM_COMPOSE_PROJECT`, default `hostmark`) with `FORWARD_ROUTES=58080=api:8080,59000=minio:9000`, so k6 still sees `127.0.0.1:58080` and `127.0.0.1:59000` and the presigned URLs stay valid, but the traffic reaches the services directly. Without that network (a stack that is not the compose one, or a wrong `HM_COMPOSE_PROJECT`) the sidecar falls back to `host.docker.internal`; `run.mjs` warns on stderr and records `forwarderRoute` (`compose-network` or `published-port`) in the result. A dial retry in the forwarder was tried and rejected: 124 of 600 connections ended in EOF in a range of 100 ports. `apps/web/e2e/forward.mjs` still uses `host.docker.internal` and has the same exposure, but its runs carry no load numbers. S5's `drained` rate also counts a window as drained only when every file is `ready`, not merely terminal.

**D130. A job made final by the file's own counter.** When only `files.attempts >= MAX_ATTEMPTS` made `process_image` final and the row was updated to `failed` (D72), the handler returns, so no DLQ copy exists. It logs `process_image failed, no DLQ copy` instead of `process_image dead lettered` (which is logged only when the platform's own counter is final and the message is rethrown), and it marks the `process_image` span as an error with the exception, because a return would otherwise end the span with an unset status. `jobs_dead_lettered` is still counted, as before (D55).

**D131. Seed order.** The seed first applies every provided value (rotation and upsert, D75) and only then looks at the unset slots. A provided value can be the key the other seed user holds; the upsert moves it, and an unset slot whose only key was moved counts as a user without a key and gets a generated one, printed once (D14). Seeding the same values again keeps the row of each key, so `files.api_key_id` links survive.

**D120. `platforms.json` and the `pnpm platform` command.** `platforms.json` is `{ "platforms": [...] }`, an array of strict objects `name`, `enabled`, `adapter` (`adapters/<name>`), `status` and `secrets`, validated with Zod in `tools/platform/schema.mjs`; the command (`tools/platform/cli.mjs`, plain ESM, Zod is the only dependency, a root devDependency) refuses to start on an invalid file. It lists `local` besides the seven platforms, so that its adapter is shown and counted, and it is disabled like the rest. `secrets` names the deploy credentials of the platform (account token, project or role identifiers, SSH key), not the application variables, which each adapter README lists (D70). An adapter lists a secret only after checking what its deploy tool reads, so the names for adapters that do not exist yet are the usual ones of each provider and change when the adapter is written. Beyond D70's `list`, `check` and `deploy`, `matrix [name]` prints the GitHub Actions matrix, so that the workflow gets the validated list and not a `jq` filter over unchecked JSON. Exit codes: 0 done, 1 refused or failed, 2 usage error or unknown platform.

**D121. What `deploy` does.** `pnpm platform deploy <name>` refuses when the platform is disabled, when its adapter directory does not exist, or when a named secret is missing from the environment. Only then does it run `pnpm --dir <adapter> run platform-deploy`, a script each adapter provides when it learns to deploy. The name is not `deploy` because pnpm has a built-in command of that name. Enabling a platform (setting `enabled` to `true` in a commit) is the owner's decision, per D71.

**D122. Workflows.** `.github/workflows/deploy.yml` runs on `workflow_dispatch` only, takes `all` or one platform name, builds its matrix with `pnpm platform matrix`, and runs `deploy` per entry (which names any missing secret), in a GitHub Environment named after the platform, which holds that platform's secrets. A named platform that is disabled fails the plan job; `all` with nothing enabled deploys nothing. The deploy step's `env` lists every secret name of `platforms.json` as a reference; a test keeps the list equal to the file (D123 for the choice input). `.github/workflows/ci.yml` runs `pnpm lint`, `pnpm typecheck` and `pnpm test` on pushes to `main` and on pull requests, for all adapters, enabled or not. An adapter directory that does not exist yet is simply absent from the workspace, so CI needs no special case for it. Neither workflow holds a secret value.

**D123. One route per platform, and what `enabled` and `status` mean.** Cloudflare is deployed by `cloudflare-production.yml` only, because that route rolls out in steps and rolls back (D142). `deploy.yml` omits Cloudflare from its choice and the plan job runs `pnpm platform matrix --exclude cloudflare`, so `all` skips it even when it is enabled; a test pins both. The other platforms use `deploy.yml`, which is not wired for credentials: it has no cloud login step and no `id-token: write`, and only `adapters/aws`, `adapters/gcp` and `adapters/vercel` have a `platform-deploy` script, so for the rest a dispatch ends in a failed job and deploys nothing. Credentials are built per platform when the owner enables it. The rule for the two flags: `enabled` is the owner's permission to deploy and to run the workflows that cost money; `status: deployed` records that a first real deployment exists, and workflows that act on a live deployment (the Cloudflare production rollout, the benchmark) require both. An enabled platform with status `emulated` can be deployed the first time but is not rolled out or measured. `deploy.yml` runs from `main` only, since a branch carries its own `platforms.json`, and sets the secrets on its deploy step alone, and no workflow expression is expanded inside a `run:` (a test checks both files). Actions are pinned to a full commit SHA with a version comment, checked against the tag with `git ls-remote --tags`. `platforms.json` lists what a deploy reads from the environment (D189 for `gcp`), not Application Default Credentials or the variables each platform stores itself.

**D132. The smoke test never builds.** All services of `adapters/local` share the image `hostmark-local:dev` with `pull_policy: build`, so a plain `docker compose up -d --no-deps worker` rebuilt a changed tree and recreated only the worker: the test then ran a new worker against the api and scheduler of the old image. Every `up` in `scripts/smoke.ts` is `--no-build`, so the test checks the stack as it was started and needs the image to exist already. The final restore of the default backoff and replica count is a step of its own, so a failure shows in the summary instead of aborting the script before it.

**D170. The benchmark is off until a platform is enabled and deployed.** `.github/workflows/benchmark.yml` runs on `workflow_dispatch` and on a monthly `schedule`, and the schedule fires by itself once the file is on `main`. Its first job, `plan`, reads `platforms.json` (D120) and `load/regions.json` through `load/tools/bench-lib.mjs` and decides which platforms may receive load: `enabled` is the JSON `true` (the string "true" is refused), `status` is `deployed` (`emulated` has nothing to measure, so enabling an unfinished adapter does not start a benchmark), and the platform is not `local` (its stack runs on the owner's machine). The job has no secret and no environment, and never contacts a platform; it ends with `count=0` and exit 0 when nothing qualifies, every later job has `if: needs.plan.result == 'success' && needs.plan.outputs.<n>_count` neither empty nor `0`, and so nothing reaches a secret, a target or anything that costs money. Anything the plan cannot read (a broken `platforms.json`, a platform that is named but disabled, unknown or `emulated`, a bad list) exits 1: unknown input never starts load. The runner mode is checked only when something would run, so a schedule on a repository where nothing is enabled stays green. `tools/platform` is not used for this gate: it needs `pnpm install` and its Zod dependency, and the gate must not depend on a toolchain that can fail before the check. `load/test/bench-plan.test.mjs` pins the gate, and its first test fails if the committed `platforms.json` ever makes the plan non-empty, so enabling a platform is a visible change.

**D171. Regions: self-hosted runners, one label per region; GitHub-hosted is one vantage point.** GitHub-hosted runners cannot be placed in a chosen region (GitHub chooses the data centre and does not document where a job lands). The free way to measure from Warsaw or Frankfurt, US East and Singapore is therefore a runner in each, registered as self-hosted with the labels `self-hosted`, `hostmark-bench` and `hostmark-<region>` (`load/regions.json`: `eu`, `us-east`, `ap-southeast`). The owner supplies them: three small machines with Docker (`load/run.mjs` runs k6 and Playwright in containers) and Node 22, in those places, on any provider, which may themselves cost money. A self-hosted runner on a public repository is a risk (it keeps its workspace between runs and runs what a workflow contains): the owner requires approval for all outside contributors or uses ephemeral runners, and keeps the runners to this repository. The workflow installs the dependencies (pnpm 12.15.0, `--frozen-lockfile`) and generates the fixtures on the runner, because S10 and S13 need `apps/web/node_modules`; those steps carry no platform credential. Distributed k6 (Grafana Cloud k6 load zones, or the k6 operator on Kubernetes clusters in three regions) was not chosen because it needs a paid account or clusters, and a runner per region needs neither. `runner_mode` is `regional` or `github-hosted` and has no default (dispatch input is required; a schedule reads the variable `BENCH_RUNNER_MODE`, and a dispatch never falls back to a variable: an empty input is empty); `github-hosted` runs everything once from `ubuntu-latest`, labels the region `github-hosted`, and the report says "one vantage point of unknown location; no regional comparison". It is a fallback for checking that the workflow works, not a measurement of regions.

**D172. Two phases per platform.** S1 to S9 need one load generator and are run from the primary region (`core`, one platform at a time, `max-parallel: 1`). S10 to S15 are the regional scenarios and run from every region in parallel (`reach`), after `core`, so that one platform is never under two loads at once. A concurrency group `benchmark` stops two runs from overlapping. Each matrix entry is one platform in one region with its scenarios, a `runs_on` label list and a timeout (150 minutes; 960 with S7).

**D173. Budgets and billing alerts are a confirmation, never a default.** The spec requires them before the first S5 and S6 (D90). The dispatch input `confirm_budgets` (or, for a schedule only, the variable `BENCH_BUDGETS_CONFIRMED`; a dispatch with an empty input confirms nothing) lists the platforms for which the owner has set a budget and a billing alert. It defaults to empty, there is no `all`, and an unknown name is an error. A platform that is not listed still runs everything else; its S5 and S6 appear in the plan as skipped with that reason and in the report as NOT RUN. The load job gets the same value again from its own `env` and `checkEntry` compares it with the entry's `budgets` flag, and `run.mjs` receives `LOAD_ACK_BUDGETS=yes` (D90) only for S5 and S6 of a confirmed platform. The confirmation is the owner's statement; nothing here checks that a budget exists.

**D174. S7 and S14 run only when named.** S7 (cold start) takes about 13 hours in its specified form (D92) and S14 measures propagation only if a deploy happens during the run (`EXPECT_VERSION`). The standard set leaves both out and the plan says why. Naming S7 on a GitHub-hosted runner is refused, because a hosted job ends after 6 hours. S15 is part of the standard set and records `skipped` when the platform has no purge API (D98); the report shows it as SKIPPED with the reason.

**D175. Credentials: one GitHub Environment per platform, read by the load jobs only.** The load jobs run in the environment `bench-<platform>` (separate from `deploy.yml`'s environments, which hold deploy credentials; the benchmark needs only the app's own keys). It holds the variable `HOSTMARK_BASE_URL` (https, a real host: `checkTarget` refuses http, credentials in the URL, a query, and loopback names) and the secrets `HOSTMARK_API_KEY`, `HOSTMARK_ADMIN_API_KEY` (handed to S8 alone) and, for S12 and S15, `HOSTMARK_PURGE_TOKEN`. `HOSTMARK_PURGE_URL`, `HOSTMARK_PURGE_METHOD` and `HOSTMARK_VARIANT` (default `portable`) are variables, not secrets. The owner restricts each environment to `main`, and the whole workflow does nothing outside `main` (`plan` has `if: github.ref == 'refs/heads/main'`, and every later job needs it). The dependency install and the fixture generator run in their own step with no secret, before the step that reads them. The owner can add required reviewers to an environment, which makes each platform's first load an approval. `bench-run.mjs` is the one step that sees them; it checks `platforms.json` and the confirmation a second time, refuses (exit 2) before any request, and hands `load/run.mjs` an environment of about a dozen variables (not the job's `GITHUB_TOKEN`). Dispatch inputs and variables reach scripts only through `env:`; a test fails if any `run:` holds `${{ }}`. Permissions are `contents: read`, and `contents: write` only on `publish`, which holds no platform secret. Actions are pinned to full commit SHAs.

**D176. Publishing: a results branch in this repository.** The simplest target that needs no account beyond GitHub is an orphan branch `benchmark-results`, pushed by the `publish` job with `GITHUB_TOKEN` (`contents: write`): `runs/<id>/run.json`, `runs/<id>/report.md` and a `README.md` that reports every run on the branch (GitHub renders it, and the JSON is the data). Also written to the job summary (the report stays under 900,000 bytes, the limit is 1 MiB) and uploaded as an artifact. GitHub Pages would need a build and a repository setting; a Gist, a database or an object store would need a second account or a token. The branch is public if the repository is, so results are public too; they hold no keys. A run id is `<run id>-<attempt>`; publishing it again replaces its files. The commit is by `github-actions[bot]`; `load/tools/bench-publish.mjs` works in a separate git worktree and refuses `main` and any odd branch name (tested against a bare repository in a temporary directory).

**D177. Merging the regions: `bench-entry.json` and `run.json`.** Each load job writes a sidecar `load/results/bench-entry.json` (the entry, run id, times, exit code per scenario) next to the result files, and uploads the directory as one artifact. `bench-merge.mjs` reads the downloaded artifacts and `plan.json` and writes one record (`kind: hostmark-benchmark-run`): every result as a flat row with platform (from the sidecar, falling back to the target's `x-platform`), scenario, region, `treeSha`, mode, validity and its headline numbers, the trees present, what the plan expected and did not get (`missing`), what the gate left out (`skipped`, `refusedPlatforms`) and a platform mismatch (the target answered as another platform than planned). Nothing is averaged or dropped at this step. Result files that are not results (behaviour records, unreadable JSON) are listed as ignored.

**D178. How the report groups results.** `load/tools/report.mjs` (input: run records, or raw result files for an ad hoc run) combines results only when platform, scenario, region, variant (`labels.variant`, else the suffix of `x-platform`), `treeSha` and load mode with its deviations are all equal; then it shows the median with the range and the count. A different tree or a reduced form is its own row, the row says "1 of N groups for this cell", and a "Read this first" section opens with MIXED TREES. A result that is `invalid` (host paused, or no watcher, D98) is counted and named but is in no number. `skipped` is SKIPPED with its reason and is not in the passed count. A group with passed and failed results is MIXED. Planned results that did not arrive, and scenarios the gate left out, are NOT RUN rows. A result without a host pause record, a dirty tree, a result without a `treeSha`, a reduced load and a run without a plan are warned about. A status that is not passed, failed, skipped or invalid is shown as UNRECOGNISED STATUS with the text it carried, counted apart and in no number; it is never dropped. The same run id given twice is counted once (the newest `generatedAt`), and so is a result row identical in cell, variant, tree, status and day; a rerun that publishes under a new attempt id with another timestamp is not recognised as a duplicate when its numbers differ, and is then a second result in the group (recorded limit). Text from result files is escaped before it reaches markdown. The files in `load/results/` from the first local runs were measured on older trees; the report shows each under the tree it names, and none of them is an E2 result.

**D179. What is proven offline, and what is not.** Proven: the gate and the second check (`bench-plan.test.mjs`), merging three regions, the report rules, publishing against a bare repository, the workflow's static rules (`bench-workflow.test.mjs`), and `actionlint` 1.7.12 on the workflow (the version the pipeline README names), and `node --test load/test/*.test.mjs` on Node 22 (a glob: Node 22 reads a directory argument as a module path). Not proven, because nothing was run on GitHub: that the labels and matrix expressions work on real runners, that `download-artifact` lays the files out as `merge` expects, that `GITHUB_TOKEN` may push the branch under the repository's settings (a branch protection rule on `benchmark-results` would block it), that self-hosted runners have Docker and Node, and that S10 and S13 run on them. The first run on GitHub should be a `github-hosted` dispatch of `S1` against one deployed platform.

**D140. Every Cloudflare workflow is off until platforms.json enables it; the gate reads the base, fails closed and runs without a secret.** `.github/workflows/cloudflare-preview.yml`, `cloudflare-preview-cleanup.yml` and `cloudflare-production.yml` start with a job `gate` that has no secret, no environment and no install step: `permissions: contents: read`, a sparse checkout of `platforms.json` and `adapters/cloudflare/pipeline/gate.mjs`, one `node` call. Every other job has `needs: gate` and `if: needs.gate.outputs.enabled == 'true'`, so with `cloudflare.enabled` not `true` the run is one green job and the others are skipped; a skipped job never evaluates its `environment:`, so no environment is created, no secret is read, no account or Neon project is touched and nothing costs money. The gate fails closed: a missing or invalid file, no `cloudflare` entry, two entries, or any `enabled` value except the JSON `true` (not the string "true") is "disabled", and disabled exits 0. Production also needs `status` to be `deployed` (`--require-deployed`; `emulated` has nothing to deploy to) and `github.ref` to be `refs/heads/main`. The preview workflows check out the BASE sha for the gate, so a pull request cannot enable the platform or change the gate by editing `platforms.json` or `gate.mjs`; they also require the head repository to equal the base repository (a fork gets no secrets from GitHub anyway) and skip `dependabot[bot]`, whose runs have no Actions secrets (amended by D145: previews are for owners, members and collaborators only, and only for pull requests into `main`). `pull_request_target` is never used. `adapters/cloudflare/pipeline/test/workflows.test.mjs` pins these rules: empty top-level `permissions`, actions pinned to full commit SHAs, the gate is the first job and holds no secret, every other job needs it, secrets appear only in a job with an environment, no `${{ }}` in any `run:` (values reach scripts through `env:`), a timeout on every job. `platforms.json` is owned by the platform opt-in (D120); this gate only reads it.

**D141. Preview model: api and consumer per pull request, a Neon branch with an expiry, one shared preview bucket.** A preview is the Workers `hostmark-api-pr-N` and `hostmark-consumer-pr-N` (the scheduler is not previewed), queues `image-jobs-pr-N` and `image-jobs-dlq-pr-N`, a Hyperdrive `hostmark-pr-N` and a Neon branch `preview/pr-N` of a preview parent branch, created with a 7-day `expires_at` so a missed `closed` event cannot leak a database for long. `preview-config.mjs` renders the per-PR wrangler configs from the committed ones with an allowlist of keys: it refuses unknown keys and service bindings outside the preview set, drops triggers, routes, `env` and `account_id`, rewrites the service binding to the preview api rewrites every queue name to its `-pr-N` form (a production queue name never survives) and refuses the production bucket. Previews have their own secrets (`PREVIEW_*` in the environment `cloudflare-preview`), their own database branch and queues, and the bucket `PREVIEW_R2_BUCKET`, which holds only preview objects and is emptied by a lifecycle expiry rule, not by the pipeline (an S3 listing and delete would need the bucket's secret in the cleanup job). Production secrets and the production database URL exist only in the environment `cloudflare-production`. The pipeline gives child processes only the credentials they need: `wrangler` gets `CLOUDFLARE_*`, the migration and the load run get none of them. The preview URL is the workers.dev one. The comment on the pull request is rendered from validated shapes only (SHA, https URL, run URL, branch name), so nothing the pull request controls reaches Markdown, and only a comment by `github-actions[bot]` carrying the marker is updated. Teardown runs every step even after a failure (consumer, api, queues, Hyperdrive, Neon), treats "already gone" as success and ends red listing what is left; it runs the BASE checkout, so closing a pull request never runs the pull request's code with the preview secrets.

**D142. Production rolls out in 10%, 50%, 100% steps and rolls back by itself when the signal is bad or absent.** `cloudflare-production.yml` runs only from `main` (D140), first migrates the production database (expand-only, as the previous version keeps serving 100% during the rollout and a rollback returns to it), then for each of api and consumer: reads the version that serves 100% now from `wrangler deployments list --json` (refuses to start unless exactly one version holds 100%), uploads the candidate with `wrangler versions upload` (`--var APP_VERSION:<sha>`, so `x-version` names the commit), probes it while it serves 0% (pinned with the `Cloudflare-Workers-Version-Overrides` header, plus an unpinned mix), shifts 10%, 50%, 100% with a soak between steps, and after 100% runs `load/run.mjs` with the short S1 and S2 (api) or S4 (consumer, which has no HTTP surface and no probe). `rollout.mjs` decides: a missing, malformed or inconsistent health signal, fewer than 20 samples, an error rate above 1% or a p95 above 1500 ms is a rollback, a thrown error in the decision is a rollback, and a rollout without a probe or a verification refuses to run (never promote blind). Rollback is `versions deploy <stable>@100`; if that fails too the outcome is `rollback-failed` and the job ends red. The scheduler is deployed directly after both are promoted (cron triggers have no percentage). Migrations that are not expand-only, and Durable Object migrations (which Cloudflare does not allow in a gradual deployment), need a manual deploy.

**D143. Limits that stay, and what the pipeline cannot do.** (1) A person with write access can edit the workflow in a pull request branch and run it with the preview environment's secrets; the base-sha gate stops fork pull requests and edits of the gate, not that. Mitigations: the preview secrets reach only preview resources, required reviewers on the environment `cloudflare-preview` make each run an approval, and a separate Cloudflare account for previews is recommended (D145: the required reviewers are mandatory, and the separate account is the real answer, because the job deploys the pull request's code with a token). (2) A Cloudflare API token cannot be scoped to one Worker or one queue prefix, so in a shared account the preview token can touch production resources; only a separate account (or a token that cannot reach the production Workers, which the Cloudflare permission model does not offer per Worker) separates them. (3) If a `closed` event is missed (an outage, a disabled workflow) the Workers, queues and Hyperdrive of that pull request stay until removed by hand; only the Neon branch expires by itself. A scheduled sweep was not written. (4) The first production deploy is manual: `deployments list` fails for a Worker that does not exist, so the pipeline refuses to start. (5) The scheduler is not rolled out gradually.

**D144. What is proven offline, and what is not.** Proven by tests against fake HTTP and fake commands: the gate (including fork and malformed input), the Neon client (failed, partial and duplicate answers), the comment text and upsert, the rollout decision and its orchestration, rendering the per-PR configs from the real wrangler files, provisioning and teardown order and idempotency, and the static rules of the three workflows; `actionlint` 1.7.12 reports nothing. Not proven, because nothing ran on GitHub, Cloudflare or Neon: the Neon endpoints (list, create, delete, connection URI, `expires_at`) (found by search, not read in the reference page by page, and never exercised), the shapes of `wrangler deployments list --json`, `hyperdrive create`/`list` and the "not found" messages, `versions deploy` with a service binding and `exports`, that `x-version` carries `APP_VERSION` on live traffic, that `wrangler delete --force` does not prompt in CI, the workers.dev URL form; the pinned action SHAs were checked against their tags afterwards by e3a-platforms, not by this stage. The first real run should be a pull request with `cloudflare.enabled` true and status `emulated`, then a manual production run.

**D145. Preview trust: pull requests into `main` by owner, member or collaborator, pipeline scripts from the base, head tree deployed.** Fixes after the review of E4. (1) Both preview workflows trigger on `pull_request` with `branches: [main]`: the gate reads `platforms.json` of the pull request's base, and a base can be any branch, so a branch with its own enabled `platforms.json` must not switch previews on. (2) The preview and teardown jobs run only when `github.event.pull_request.author_association` is `OWNER`, `MEMBER` or `COLLABORATOR`. That replaces the `dependabot[bot]` actor test and also skips Renovate and any outside contributor; a pull request of theirs gets no preview. (3) The preview job checks out the BASE sha into `trusted/` and the head sha into `head/`. The pipeline scripts (`cli.mjs` and everything it imports) run from `trusted/` and are pointed at `head/` with `HOSTMARK_ROOT`, so editing the scripts in a pull request changes nothing about what runs with the secrets. Install and build run in `head/` in steps with no secret. (4) What stays inherent: the job deploys the pull request's own code with a Cloudflare token (`wrangler deploy` of the head's built Worker, started through the head's `node_modules`), so a pull request can run arbitrary code in that account with that token. The base checkout narrows what the pipeline does, not what the deployed code can do. The real answer is the separate Cloudflare account for previews (D143 (2)), and required reviewers on the environment `cloudflare-preview` are now a requirement, not a suggestion (each push waits for an approval). The cleanup workflow only ever ran the base and needs no change besides (1) and (2). A pull request can still edit the workflow file in its own branch (GitHub runs the merge result's workflow), which is why the reviewers and the separate account matter more than the checkout split.

**D146. A failed, cancelled or timed-out production run puts the previous versions back.** `cloudflare-production.yml` records, before the migration, the version serving 100% of the api and of the consumer (`cli.mjs snapshot`, outputs `api` and `consumer`; it refuses when either is unclear, before anything changed). The last step of the `deploy` job runs `cli.mjs restore` with `if: always() && job.status != 'success' && steps.snapshot.outcome == 'success'`: `always()` makes it run on a cancel and on a timeout, `job.status` skips it on success, and the snapshot condition skips it when nothing was recorded. It restores the consumer first and then the api, to the recorded versions (`versions deploy <id>@100`), leaves a Worker that already serves its recorded version alone, tries both even if the first fails, and exits 1 if either fails. This closes three gaps of D142: a consumer rollback that left the api on the new version (the api now goes back too), a cancelled or timed-out run that left a 10% or 50% split, and a crash of the runner between steps. Accepted consequence: if only the scheduler deploy fails after both Workers were promoted, the job is red and the restore also puts the api and the consumer back, so production returns to the previous version rather than staying on a half-deployed one. The database stays migrated (expand-only, D142). The scheduler is not restored by the pipeline. Manual recovery, when the step itself fails or the runner is gone, is in the pipeline README ("Manual recovery"): `wrangler versions deploy <previous id>@100 --config wrangler.<role>.jsonc` for each Worker. That `always()` steps run on a cancel and on a timeout of the job is GitHub's documented behaviour, but it was not exercised here.

**D147. Production verification inputs, and tests that fail when the policy changes.** The `deploy` job runs `node load/tools/fixtures.mjs` (no secret in that step) after the install and build and before the first rollout: the upload scenario S4 (the consumer's gate) reads generated fixtures from `load/lib/fixtures.js` that no other step creates, and the review found the same precondition for the verification as a whole, so without it a verification could fail and roll back a healthy release. Whether S1 and S2 alone need them was not checked; the step is cheap and harmless there. The tests of the rollout now assert the action at every threshold of `DEFAULT_POLICY` (19 and 20 samples, 1% and just above, 1500 and 1501 ms), pin the policy to its exact values and freeze, cover unhealthy-at-100%, and run `cli.mjs` against a fake `exec` for the exit code of promoted, failed verification, failed first deploy, failed rollback, and a failing `deployments list` or `versions upload` (each with otherwise valid output). 25 mutations of the pipeline (verification always ok, exit 0 on a rollback, ignored exit codes, a changed threshold or soak, no probe at 100%, a fail-open decision) are all caught. The new CLI tests found a real defect in `deployArgs`: it returned `['versions', 'deploy', ...]` without the leading `wrangler`, so `realExec` would have run a program called `versions` and every production rollout would have failed on the first deploy and then failed its rollback. It now returns a complete command line and a test pins that.

**D148. The spec's preview tests are not implemented.** The spec (CI/CD and preview environments) lists "Preview tests: smoke test upload to `ready`, browser test S13" after the preview is up. The E4 pipeline does not run them: a preview run ends with the health poll of `/api/health` and the pull request comment. They need a preview that processes an image, which means the consumer and the queue of that preview plus a browser and k6 on the runner, and they cannot be tried offline. The production rollout does run the short scenarios S1, S2 and S4, which cover upload to `ready` against production, but no workflow runs S13 and none runs any scenario against a preview. This is a gap against the spec, not a decision to leave it out; the first real preview run should add them.

Proof run: typecheck and lint clean, the unit and contract tests of node-runtime and local with Redis and MinIO stand-ins (44 and 27 passed, the same two queue `consume` tests skipped by the harness as before the move), a full image build and the smoke test on the compose stack (15 of 15 steps).

**D152. **D157. **D158. The client address header is fixed by the adapter.** `src/platform.ts` of every deployed Node adapter sets `AUTH_CLIENT_IP_HEADER` and ignores the environment: `X-Client-Ip` (vps, written by Caddy from the TCP peer), `Fly-Client-IP` (fly) and `X-Real-IP` (railway; documented, but that the edge overwrites a client-sent value is unconfirmed and must be tested on the first deployment). **D159. One scheduler, enforced where the platform allows it; the rest is not measured.** VPS: one compose service without replicas, tested. Railway: `numReplicas: 1` and `overlapSeconds: 0` in `services.json`, tested as values only (the settings are entered by hand, D157). **D100. A CDN purge port.** `CachePurger { purge(paths) }` in `packages/core/src/ports.ts`, an optional `purger` in `CoreDeps`, and `publicPaths(fileId)` (`/media/:id/` and `/f/:id`) in core. `/media` is cached for a year as immutable (D6), so leaving public is not enough: `PATCH` to private purges after the row is private and answers 503 if the purge fails, and the same `PATCH` again retries it (the row is already private, so a retry is safe and the 503 says so). `DELETE` purges best effort, because a retry of `DELETE` would answer 404; the `delete_file` job awaits the purge again before it removes the objects, and a failure there retries the job. A platform without a CDN passes no purger and nothing changes. Cloudflare: Workers Caching purges only the entries of the entrypoint that calls `purge`, so the api Worker exports a `Media` entrypoint (`exports.Media.cache.enabled`) that serves the cached paths and owns `purge`; the consumer and the scheduler reach it through the service binding `MEDIA` (`hostmark-api#Media`). `createWorkersCachePurger` throws `ConfigError` when the `MEDIA` binding has no `purge` method, so a consumer or scheduler without the service binding does not start, and `pnpm check` (`scripts/check-config.ts`) asserts the wiring (`MEDIA` points at `hostmark-api#Media`, `exports.Media.cache`) before a deploy. An earlier refusal in `createScope` ("no purger outside local") could not fire, because every Worker passes an object, and was removed. Proven: the ports in core tests, the 503 after a purge that did not happen on the real bundles in workerd, the missing-binding refusal in a unit test. Not proven: that `cache.purge({ pathPrefixes })` empties the cache on Cloudflare; local workerd has no Workers Caching (`ctx.cache` is undefined), so it needs a real account. Only the canonical lowercase id is served from `/media` and `/f` (D107). The other CDN adapters implement the same port. Known gaps, all to close before any public deployment (`docs/plan.md`, E3): (C) there is no purge route for S12 and S15 and no `PURGE_URL`, and a zone purge does not affect Workers Caching, so those scenarios cannot run against this variant as they are. (E) The purge API allows 5 prefix purges a minute per account on the Free tier (100 operations per request): an unpublish costs 1 call, a delete 2, `PATCH` purges even a file that was never public, and `delete_file` purges every deleted file, so a burst is throttled and the jobs that fail go to the dead letter queue. (F) There is no durable retry of a purge that failed in `PATCH`: the caller must send the same `PATCH` again. Limiting the purge to a public to private transition would break exactly that retry after a 503, so E and F need a `purge_pending` marker and a migration, which is not added without review. (L) `?x=1` answers 200 and is cached as its own entry, so a CDN that keys on the exact URL needs care. (N) Rollback and old-version cache entries are untested.

**D101. Queues has no visibility timeout.** Push consumers on Cloudflare Queues have none: a message is held for the invocation, and a handler that exceeds the invocation limit is cancelled and the message retried. The queue contract (`packages/core/test/contract/queue.ts`) takes optional `firstRetryDelaySeconds` and `visibilityTimeoutMs`; the Cloudflare adapter sets the first and leaves the second out, so that test is a visible skip, not a pass. The contract now tests the wait after the first failed attempt (`BACKOFF_SECONDS[0]`), and an adapter that has a visibility timeout passes `visibilityTimeoutMs` to run the redelivery test; adapters that pass neither skip visibly. The stall tests live in `packages/node-runtime/test/stall.test.ts` and run against the node runtime's BullMQ queue; they are not changed by this, and `adapters/local` has none of its own any more. Attempts count from 1 (`message.attempts`); `max_retries` is `MAX_ATTEMPTS - 1` and the dead letter queue is `image-jobs-dlq`, both compared with `@hostmark/contract` by `pnpm check`.

**D102. Workers: a database client per request, no telemetry SDK.** A Workers isolate cannot carry a socket from one request to the next, so each request or invocation builds a `postgres` client (`max: 5`, `fetch_types: false`, `prepare: true`, behind Hyperdrive) through `databaseFromPostgresJs` (`@hostmark/db/postgres-js`) and closes it after the response body ends (an SSE stream keeps it until it ends). The app and its routes are built once per isolate. `@hostmark/telemetry` has no SDK provider on Workers here: spans and metrics are no-ops, logs are JSON lines on `console`. That is a gap in what the Cloudflare variant reports, not a silent success. The Better Auth rate limiter counts in memory per isolate (D80), so it limits per isolate and not per client.

**D103. Workers image size limit: 1.5 MP, measured in workerd and derived, not enforced.** `WORKERS_MAX_PIXELS = 1_500_000` in `adapters/cloudflare/src/limits.ts`, passed to `createWasmImageProcessor`. Measured in workerd (Miniflare 4.20260730.0, the real bundle, in a Linux container): the WebAssembly memory the codecs hold is about 23 bytes per pixel, 13 MB at 0.25 MP, 31 MB at 1 MP, 42 MB at 1.5 MP, 51 MB at 1.9 MP, then a step to 106 MB at 2 MP, 157 MB at 4 MP, 340 MB at 12 MP. Isolates get 128 MB for the JavaScript heap and the WebAssembly memory together, so the range of 12 to 16 MP in D31 is wrong by a factor of about eight, and the 4000x3000 fixture of the load tests is refused by this variant. Local workerd does not enforce the 128 MB, so no failure was observed; 1.5 MP keeps wasm memory under 45 MB and leaves room for the heap and garbage. Not measured: where a real isolate runs out, and the true cost of a variant. The portable variant therefore cannot be compared on the 12 MP image; a different image path is needed for that (the E4 and later work), not a larger limit. `test/image.test.ts` checks that the default limit refuses an image above it by header and accepts one below it. Consequence for the load tests, stated plainly: on this variant only the `jpeg-tiny` fixture passes. `jpeg-1mb` (4000x3000), `png-10mb` (3.33 MP), `jpeg-50mp`, `png16-49mp`, `webp-49mp` and `png-tall-49mp` are refused. Scenarios S4, S5, S9, S12, S13 and S15 therefore fail or cannot set up (S4 fails `upload_ok`, S5 fails `drained`, S9 refuses every upload, S12 and S15 throw in setup because `seedPublicFile` uses `jpeg-1mb`, S13 cannot reach ready); S1, S2, S3, S6, S7, S8, S10, S11 and S14 use no large fixture. Acceptance criterion 4 (all scenarios without a change to test code, spec line 690) is not met by the portable Cloudflare variant, and ordinary phone photos are refused while `MAX_UPLOAD_BYTES` stays 10 MB. The fixtures are not shrunk and there is no per-platform override; whether to accept this is an owner decision (Open items). Headroom, from the same measurements: PNG would have 50 to 53 MB left (JPEG 42 MB at 1.5 MP), the consumer sets no `max_concurrency`, and the JavaScript heap is not measured. Tests run on workerd 1.20260730.1 (Miniflare 4.20260730.0) while wrangler 4.156 deploys against 1.20261023.1, so a limit measured here may differ in production.

**D105. Static wasm, licences, and the test setup.** The wasm codecs are imported statically (`src/wasm-loader.ts`, `CompiledWasm` modules), as `@hostmark/image` documents. **D190. AWS: CloudFront in front of a Lambda function URL, protected by an origin secret.** `adapters/aws` is plain CloudFormation (`template.yaml`, no SAM transform). The api is one Lambda behind a function URL with `AuthType: NONE` and `InvokeMode: RESPONSE_STREAM` (SSE needs streaming). Origin access control was rejected for the function URL: it signs requests, and a POST or PUT then needs `x-amz-content-sha256` from the client. CloudFront adds the origin custom header `x-hostmark-origin-secret` and the api answers 403 without it (constant-time compare). Anyone with the function URL and the secret bypasses CloudFront; rotation is a stack update. The web app is an S3 origin with OAC under the `site/` prefix of the content bucket, with a CloudFront Function for single page app routes. `/api/*` is uncached with Compress off (SSE); `/media/*` and `/f/*` follow the origin `Cache-Control` (D6). Proven offline: the 403 and 200 on the built bundle, the template checks, the CloudFront Function in `node:vm`. Not proven: any of it through a real distribution.

**D191. AWS: three Lambdas, two deploy passes.** api (1024 MB, 90 s), worker (3008 MB, 60 s, SQS batch size 1, `ReportBatchItemFailures`, max concurrency 10) and scheduler (512 MB, 120 s), `nodejs22.x` on arm64, one postgres.js connection per environment (`max: 1`). A Lambda environment cannot refer to the distribution that refers to the function, so pass one deploys with an empty `DistributionId` and pass two sets `DistributionId` and `PublicUrl`; the deploy script does both, and outside `ENVIRONMENT=local` a function refuses to start without the distribution id (D100). Secrets Manager was not used; the values stay `NoEcho` parameters and are readable in the Lambda configuration. `hono/aws-lambda` `streamHandle` is deprecated in Hono 4.13 in favour of `@hono/aws-lambda`; it is kept until the replacement is checked, and only `src/api.ts` changes.

**D192. `@hostmark/storage-s3` accepts a session token.** Lambda role credentials are temporary and need `AWS_SESSION_TOKEN`; `S3StorageOptions.sessionToken` is optional and is passed to `AwsClient` and the presign signer. Nothing else in the package changed. This is the only change outside `adapters/aws` besides docs and the lockfile.

**D193. AWS: SQS backoff through `ChangeMessageVisibility`.** SQS has no per-message delay on retry. The worker maps `ApproximateReceiveCount` to `ctx.attempt`, sets the visibility to `BACKOFF_SECONDS[attempt - 1]` for a failing job and reports it as a batch item failure; on attempt 5 it sets the visibility to 0 so the redrive policy (`maxReceiveCount: 5`) moves the message to the dead letter queue at the next receive. `crash()` throws out of the handler, so the message returns only after the queue visibility timeout, 360 s (6 times the worker timeout, the AWS rule): crash recovery takes about 6 minutes here, longer than on the other platforms. A send delay above 900 s throws (the SQS limit). Proven on ElasticMQ with a poller that behaves like the event source mapping (the core queue contract, backoff scaled by `QUEUE_BACKOFF_SCALE`); not proven against real SQS and Lambda.

**D194. AWS client address header: `x-hostmark-client-ip`, set by a CloudFront viewer-request Function.** The function writes `event.viewer.ip` and overwrites any client value, on every behavior that reaches the Lambda URL; the api is reachable only with the origin secret (D190). `X-Forwarded-For` is appended to by CloudFront and `CloudFront-Viewer-Address` carries `ip:port`, which fails the single-address check of D80. Whether the value is the real client address on every viewer network is from the documentation and must be tested on a real distribution.

**D195. AWS purge: `CreateInvalidation`, with wildcard paths.** `createCloudFrontPurger` (`CachePurger`, D100) invalidates the file's `/media/<id>/*` and `/f/<id>` paths (collapsed by `compactPaths`, in chunks of 3000), client in `us-east-1`. A failure throws, so core answers 503. The IAM statement allows `cloudfront:CreateInvalidation` on the one distribution. The first 1000 paths a month are free; propagation time is not measured.

**D196. AWS storage and schedule.** One content bucket: `originals/` and `variants/` expire after 8 days (D74), `site/` never; CORS for GET and PUT, SSE-S3, TLS-only policy; the CloudFront OAC reads `site/*` only. EventBridge Scheduler fires the three `SCHEDULER_JOBS` once per tick with `{"job":"<name>"}` and `MaximumRetryAttempts: 0`, so there is no replica to limit (D159). Wasm codecs are copied next to the bundle and compiled at cold start. Status stays `emulated`; `platforms.json` and `deploy.yml` name `ORIGIN_SECRET` for AWS since the E7 fix round.

**D180. GCP queue: Pub/Sub, pulled with the unary API.** `adapters/gcp/src/queue.ts` publishes (5 s timeout, so a down Pub/Sub makes core answer 503, D52) and `src/consumer.ts` pulls with `Pull`, `Acknowledge` and `ModifyAckDeadline`, not the client library's streaming subscriber, so that the rules of D17 stay in our hands. The subscription ack deadline is the visibility timeout (60 s); a timer renews it for the messages a handler holds (at most `LEASE_MAX_SECONDS`, 600), and a dead process stops renewing. A failed attempt sets the ack deadline to `BACKOFF_SECONDS[attempt - 1]`, the last one nacks and the subscription's dead letter policy (`max_delivery_attempts = 5`, a dead letter topic with a 7 day pull subscription) takes the message. The attempt number is `deliveryAttempt`, which Pub/Sub sets only on subscriptions with a dead letter policy and documents as approximate; `files.attempts` stays the authoritative bound (D17). Pub/Sub has no delayed delivery: a delayed `send` (production sends none, only the contract tests) carries a `notBefore` attribute and the consumer holds it back with the ack deadline, which caps the delay at 600 s and costs one counted delivery. No change to the `Queue` port.

**D181. GCP compute: services for api and worker, Cloud Scheduler for the schedule.** The worker is a Cloud Run service, not a worker pool, because pools are in Preview (checked in the documentation 2026-11-01). It runs with instance-based billing (`cpu_idle = false`), min = max = `worker_instances` (2) and `WORKER_CONCURRENCY=1` (D97); request-based autoscaling cannot see a queue, so the count is fixed. It listens on `PORT` for `/healthz` only, which pings the topic. The three `SCHEDULER_JOBS` are Cloud Scheduler jobs that call the Cloud Run Jobs API (`jobs/<name>:run`) of one job per name, `max_retries = 0`. The platform schedules, so there is no scheduler replica to limit (plan, E5); a tick that finds the previous run still going is safe because of the database claims (D19). Migrations and the seed are Cloud Run Jobs of the same image.

**D182. GCP client address: `X-Client-Ip` from the load balancer.** The backend service sets the custom request header `X-Client-Ip: {client_ip_address}`; the documentation states that headers added by the load balancer overwrite any existing header of the same name, which is the property D80 needs, and `X-Forwarded-For` does not have it (the load balancer appends to a client's value). The api service has `ingress = internal-and-cloud-load-balancing` and its `run.app` URL disabled, so no request reaches it without passing the load balancer. The documentation settles the overwrite rule; that it holds for every viewer network, and that the value is a single address, must be tested on a real deployment.

**D183. GCP storage: the Cloud Storage XML API through `createS3Storage`.** An HMAC key of the runtime service account signs with SigV4 (`S3_ENDPOINT=https://storage.googleapis.com`, region `auto`), for server calls and presigned URLs. The D74 lifecycle (`originals/` and `variants/`, 8 days) and the CORS rule are in the bucket resource in Terraform, not in an `init-bucket` step: the XML API takes lifecycle in Cloud Storage's own format, not the S3 one. The storage contract ran against MinIO as a stand-in; whether Google's signing, `Content-Length` binding of presigned PUTs (D10) and per-key delete behave the same is unproven until a real bucket is used.

**D184. GCP purge: `urlMaps.invalidateCache`.** `createCloudCdnPurger` (`CachePurger`, D100, `src/purge.ts`) calls the Compute API once per path of `publicPaths()` with the token of the runtime service account from the metadata server, and rejects when any call is refused, so core answers 503 and the caller retries. Accepted means the request was taken; the documentation says an invalidation takes effect in about 10 seconds and allows 500 requests a minute, neither measured. The runtime holds a custom role with `compute.urlMaps.invalidateCache` only. Cloud CDN is on the one backend service in `USE_ORIGIN_HEADERS` mode, so the api's `Cache-Control` decides what is cached.

**D185. GCP runtime is the adapter's own.** `createRuntime` of `packages/node-runtime` builds a BullMQ queue, so `adapters/gcp/src/runtime.ts` repeats its wiring (about 80 lines) with Pub/Sub and the purger and reuses `onTerminate`, `systemClock` and the static handler. A queue factory in `NodePlatform` would remove the copy; that package is not this adapter's to change (report to the lead). The Pub/Sub client stays external in the bundle (gRPC and its protos load from disk) and comes from `pnpm deploy --prod` in the Dockerfile.

**D186. GCP secrets and database.** `DATABASE_URL` is the shared Postgres of D70, so there is no Cloud SQL. `DATABASE_URL` and `BETTER_AUTH_SECRET` are Secret Manager secrets whose values `scripts/deploy.sh` adds from the owner's environment before the services exist; the HMAC key is created by Terraform and lands in the state, which therefore must stay private. Nothing secret is in the repository.

**D187. GCP test stand-ins.** The queue contract runs against the official `google-cloud-cli:emulators` Pub/Sub emulator (`PUBSUB_EMULATOR_HOST`), which honours dead letter policies and `deliveryAttempt` as far as these tests exercise them, with the subscription shaped like the Terraform one except that the consumer runs at 10 % of the backoff, 3 s of lease renewal and a 10 s ack deadline (the minimum). The storage contract runs against any S3 server (`S3_TEST_ENDPOINT`). Without the variables both show as skipped; the image contract always runs.

**D188. GCP status.** `emulated`. Not measured: the event loop block on a real instance, a successful CDN invalidation and its propagation, presigned URLs against Google, the 60 s ack deadline and 10 s to 600 s `ModifyAckDeadline` on the real service, `deliveryAttempt` accuracy, the load balancer header on a real request, the managed certificate and the cost. `terraform validate` was not run (the sandbox denied `terraform init`, which downloads the provider); `terraform fmt` was, and `scripts/check-config.ts` compares the Terraform with the contract constants offline.

**D189. GCP secrets in `platforms.json`.** The deploy needs `GCP_PROJECT`, `DOMAIN`, `DATABASE_URL`, `BETTER_AUTH_SECRET` and Application Default Credentials on the machine that runs `scripts/deploy.sh`; no key file is stored anywhere. `platforms.json` lists the first four for gcp.

**D106. Hyperdrive query caching is off.** Hyperdrive caches read queries by default (`max_age` 60 s, `swr` 15 s) and writes do not invalidate that cache, so a file that was just made public, private or deleted could be read in its old state for up to a minute by the api, and a job could read a stale row. `hyperdrive create` and `hyperdrive update` therefore pass `--caching-disabled` (the flag exists on both) in `adapters/cloudflare/README.md` and `adapters/cloudflare/pipeline/provision.mjs`; the pipeline test asserts it on both calls. `prepare: true` in `runtime.ts` stays: per the Opus review, what makes a query uncacheable is Postgres.js with `prepare: false`, so with caching off the setting has no effect on correctness and stays. Not measured: a deployed Hyperdrive.

**D107. `/media` and `/f` serve the canonical lowercase id only.** `packages/core/src/http/app.ts` answers 404 unless the id in the raw request path is the canonical lowercase UUID. Before, `/media/<UPPERCASE-ID>/128.webp` and a percent-encoded first character (`%41...`) were accepted and normalised, so the same file could be cached by a CDN under several paths and a purge of `publicPaths()` would miss the aliases (D100). The change is that one behaviour. The core test `http.test.ts` that expected an uppercase id to answer 200 now expects 404 (named "refuses an uppercase id (D100)..."), and `purge.test.ts` serves the canonical paths and refuses both aliases on `/media` and `/f`. Other adapters with a CDN get the same behaviour.

**D197. Vercel files: an external S3 compatible bucket (Cloudflare R2), not Vercel Blob.** `adapters/vercel` uses `@hostmark/storage-s3` against R2 (`S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, region `auto`). Reasons: the `ObjectStorage` port needs presigned PUT and GET and a lifecycle rule for D74, and the documentation read does not show an S3 API or presigned URLs for Blob (not verified); a function body is capped at 4.5 MB, so uploads must go straight to the store; reusing `createS3Storage` adds no new storage code to compare. The bucket lifecycle rule (8 days for `originals/` and `variants/`) is set on R2 by the owner (the R2 lifecycle API was not checked here: not verified). The cost is a second vendor in the Vercel row, which the owner may prefer to avoid: then a `ObjectStorage` for Blob has to be written and the contract run on it.

**D198. Vercel queue: `@vercel/queue`, own dead letter topic, retry through the `retry` option.** The producer is `createVercelQueue` (`send` with `idempotencyKey` = job id, `sendBatch` in chunks of 100, an entry the platform refused fails the call). The consumer is a `handleCallback` route (`api/queue.ts`) declared in `vercel.json` with `experimentalTriggers` of type `queue/v2beta` (the published schema confirms the shape). `attempt` is `deliveryCount`. A throw is retried after the D17 backoff through the synchronous `retry` option (`BACKOFF_SECONDS`); Vercel Queues has no dead letter queue, so on attempt `MAX_ATTEMPTS` (and for a body that is no job message) the payload is first sent to the topic `<topic>-dlq` and the delivery then returns normally, which acknowledges it; if the dead letter send fails the delivery throws and is retried. The dead letter topic has no consumer (checked by `pnpm check`). `chaos=crash` throws and is always retried. The queue is Beta and has no local stand-in without an account, so the contract runs on `test/stand-in.ts`, an in-memory model of the documented semantics; it proves the adapter logic only. Not verified: at-least-once delivery and idempotency key semantics, the visibility timeout the consumer runs under (default 60 s, longer than a normal image job but not configurable in `vercel.json`), `vercel dev` as a local queue.

**D199. Vercel purge, cache and client address.** Public `200` answers of `/media/*` and `/f/*` get `Vercel-CDN-Cache-Control: public, max-age=31536000, immutable` and `Vercel-Cache-Tag: file-<uuid>`; `createVercelPurger` (D100) calls `dangerouslyDeleteByTag` of `@vercel/functions` with the default deadline, which removes the entries at once. `invalidateByTag` is not used because it marks entries stale and revalidates in the background, so an unpublished file could be served once more. Which call stops serving an unpublished file on a real deployment is not measured. `clientIpHeader` is `x-vercel-forwarded-for`: the documentation says Vercel overwrites `x-forwarded-for` and does not forward external addresses, and that `x-vercel-forwarded-for` is identical to it; test on a real deployment that a spoofed header is replaced. Scheduler: Vercel Cron calls `GET /api/cron?job=<name>` with `Authorization: Bearer $CRON_SECRET` (compared in constant time, any other job name is refused); there is no replica to limit, a run can be delivered twice and the jobs tolerate it (D19). The 5 and 15 minute schedules need Pro; on Hobby cron runs once a day (and Hobby is non-commercial), so a Hobby deployment fails `vercel deploy` or loses the schedule. Status stays `emulated`; `platforms.json` and `deploy.yml` were extended with the Vercel variables at the lead's order. Deploy and secrets: `scripts/deploy.mjs` (`platform-deploy`, reached by `pnpm platform deploy vercel`, D70) runs the `vercel` CLI; secret values go only to the CLI's stdin (`vercel env add NAME production`) or its environment, never argv, and CLI output is scrubbed of them; `test/deploy.test.ts` proves it with a fake `vercel`. The Vercel project's Root Directory is `adapters/vercel`, `vercel.json` build commands step up to the monorepo root. AWS likewise: `AWS_CODE_BUCKET` replaces `--code-bucket` so `pnpm platform deploy aws` works, and `platforms.json` and `deploy.yml` name `AWS_CODE_BUCKET`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `ORIGIN_SECRET` for aws and the eleven names of the vercel README.

**D200. GCP: url map name and queue ping.** `CDN_URL_MAP` comes from the literal `local.url_map`: a reference to the url map resource made `runtime_env` depend on the api service through the backend, and the api service iterates `runtime_env`, which Terraform refuses as a cycle. The runtime account also gets `roles/pubsub.viewer` on the topic, because `queue.ping` reads the topic metadata and `roles/pubsub.publisher` and `roles/pubsub.subscriber` do not include `pubsub.topics.get`; without it `/healthz` of the worker answers 503 and its startup probe fails. `scripts/check-config.ts` pins both. Both come from a reference graph and role documentation; neither `terraform validate` nor a real project has run them. Terraform state holds the HMAC secret, so `.gitignore` and `.dockerignore` exclude it.

**D201. Dependency build scripts: an explicit allowlist.** pnpm 12 refuses an install with `ERR_PNPM_IGNORED_BUILDS` when a dependency has an install script that is not approved, so `pnpm install --frozen-lockfile` failed in CI from the first run. pnpm 12 reads the approvals from `allowBuilds` in `pnpm-workspace.yaml`, a map from package name to `true` (run) or `false` (ignore, silently); `onlyBuiltDependencies` of pnpm 10 is not the key any more (checked in the pnpm 12.15.0 binary and its hint text). The map allows exactly `esbuild`, `msgpackr-extract`, `protobufjs` and `workerd`, the four packages of the lockfile with install scripts; `dangerouslyAllowAllBuilds` is not used. A new dependency with a script therefore fails CI until it is named here, as `true` or as `false`. The Dockerfiles no longer set `pnpm_config_strict_dep_builds=false`, so an image build applies the same rule (the local and gcp images were built with it).
